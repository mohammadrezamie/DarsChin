# ایزوله‌سازی درخواست‌های ناهم‌زمان نیازسنجی و امنیت تغییر نقش

**تاریخ:** ۲۰۲۶/۱۰/۲۶  
**دامنه:** پنل نیازسنجی دانشجو و مدیر؛ فقط مخزن درس‌چین.  
**قانون:** اطلاعات دانشجویی و گزارش شخصی مدیر نباید به context جدید «منتقل» شوند یا توسط یک درخواست قدیمی بازنویسی شوند.

## باگ‌های کشف‌شده
1. پاسخ HTTP قدیمیِ فهرست فرم‌ها ممکن بود بعد از درخواست جدید برسد و فهرست/انتخاب فرم و گزارش مرتبط را قدیمی کند.
2. جابه‌جایی بین فرم‌ها ممکن بود تا دریافت پاسخ جدید، انتخاب‌های دانشجو یا آمار فرم قبلی را روی صفحه نگه دارد.
3. تغییر چارت ممکن بود روابط پیش‌نیاز متعلق به چارت قبلی را برای چارت جدید معتبر نشان دهد.
4. **مرز هویت/نقش**: اجرای پاک‌سازی در `useEffect` بعد از نخستین render است؛ تغییر نقش، شناسهٔ حساب یا مجوز/محدودهٔ مدیریتی باید *پیش از نخستین render فضای کاری* آن را از نو mount کند.
5. هنگام بازنشانی نقش، پیش‌فرض انتخاب ترم و چارت نباید از مقدار stale محبوس در closure تابع refresh پیروی کند.

## قرارداد اجرایی
- `createRequestEpoch()` تمام refreshهای قدیمی را بعد از آغاز refresh جدید یا unmount نامعتبر می‌کند.
- در جابه‌جایی فرم، علاوه بر پاک‌سازی effect، کلید `demandDetailKey(role, surveyId, revision)` **در همان render** بررسی می‌شود؛ فقط پاسخ با کلید settled یکسان و وضعیت `ready` اجازهٔ نمایش گزارش، انتخاب درس، شماره دانشجویی و خوداظهاری ترم آخر را می‌دهد. در غیر این صورت فقط وضعیت بارگذاری/خطا و فرم غیرفعال نمایش داده می‌شوند.
- بارگذاری ناموفق detail حالت `error` و کنترل retry دارد و ذخیرهٔ پاسخ بدون detail موفق مجاز نیست.
- شناسهٔ چارت بارگذاری‌شده با شناسهٔ چارت مورد نیاز برابر باشد؛ در غیر این صورت فهرست شروط معتبر شناخته نمی‌شود.
- پوستهٔ `DemandWorkspace` با کلید مبتنی بر role، user ID، roles، permissions و demandScopes، component داخلی را **با تغییر principal از نو mount** می‌کند. این کار جایگزین مجوزسنجی سرور نیست.
- پاک‌سازی role، تمام draft، شماره دانشجویی، وضعیت ترم آخر و آمار/چارت قدیمی را صفر می‌کند؛ `refresh(true)` پس از پاک‌سازی، ترم و چارت پیش‌فرض را از دادهٔ جدید بازمی‌یابد.
- سیاست‌های دانشگاه، اطلاعات اکانت واقعی، API permission checks، محیط استقرار و مخزن تکین تغییر نمی‌کنند.

## شواهد و محدودیت
- روی **فایل‌های متن دقیق دریافت‌شده از GitHub** در محیط ایزولهٔ Vercel Sandbox با Vitest واقعی، `tests/demand-workspace-races.test.ts` با **۱۰/۱۰ آزمون موفق** اجرا شد (۶ آزمون اولیه + ۲ مرزبندی هویت/پاک‌سازی پیش‌فرض‌ها + ۲ آزمون جدید key معتبر فرم در render). رفتار تابع `isCurrentDemandDetail` برای تعویض فرم، role، revision و حالت خطا به‌صورت واقعی اجرا شد؛ آزمون UI/مرورگر کامل هنوز باقی است.
- TSX فایل تغییرکرده با TypeScript `transpileModule` بدون خطای نحوی تبدیل شد. این **جایگزین `tsc` جامع یا تست تعامل واقعی مرورگر نیست**.
- برای ادغام: اجرای `bun run qa:full` روی SHA همین شاخه، بررسی مرورگری تغییر نقش سریع، بازگشت آفلاین/خطای شبکه، اصلاح احتمالی ترم/چارت با دادهٔ واقعی فقط در محیط مجاز و عدم مخلوط شدن دادهٔ مدیر/دانشجو لازم است.
- دامنهٔ Preview Vercel با سقف انتشار روزانه مواجه شد؛ این تغییر ادعای deploy جدید یا VPS ندارد.

## راهنمای تست دستی با دادهٔ ساختگی
1. در دموی دانشجو نیازسنجی اول را انتخاب کن، پاسخ را ببین و بلافاصله فرم دوم را انتخاب کن. پیش از جواب API دوم، پاسخ اول نباید قابل ذخیره یا نشان‌داده‌شدن به‌عنوان جواب فرم دوم باشد.
2. در نقش مدیر بین دو گزارش سریع جابه‌جا شو؛ گزارش و نمودار فرم اول نباید روی فرم دوم باقی بماند.
3. نقش مدیر/دانشجو و هویت آزمایشی را تغییر بده؛ فرم‌ها، شماره دانشجویی، دروس انتخابی و آمار سابق نباید حتی به‌طور موقت زیر هویت جدید ظاهر شوند.
4. ارتباط را قطع کن: وضعیت خطا و retry، بدون فعال شدن دکمهٔ ذخیره با دادهٔ مانده از فرم قدیمی.

## تکمیل P0: راستی‌آزمایی جواب دریافت/ذخیره و جلوگیری از تأییدیهٔ قدیمی — ۲۰۲۶/۱۰/۲۶

- موفقیت HTTP دیگر به معنی قبول مستقیم پاسخ نیست. تابع مستقل `isDemandResponseForContext` قبل از نمایش پاسخِ GET و قبول تأییدیهٔ PUT، `userId`، `surveyId`، `studentNumber`، وضعیت خوداظهاری و یکتایی/عضویت همهٔ `courseIds` در فرم انتخاب‌شده را بررسی می‌کند؛ نبود جواب (`null`) فقط برای کاربر احرازشده و شناسهٔ فرم معتبر مجاز است. هیچ قانون رسمی دانشگاه در این تابع تعریف نشده است.
- `submit` فقط روی فرم `OPEN` و detail معتبر و در نبود ذخیرهٔ هم‌زمان اجرا می‌شود؛ یک epoch و کلید فعلی فرم هنگام بازگشت درخواست کنترل می‌کنند تا پاسخ دیررس، پیام موفقیت یا دادهٔ فرم دیگر را به پنل فعلی وارد نکند. با unmount، epoch ذخیره نامعتبر می‌شود.
- شکست تطبیق، پیام خوانا و حالت محافظه‌کارانه دارد: کاربر به بارگیری دوباره هدایت می‌شود؛ دادهٔ خصوصی جعلی/متعلق به فرم دیگر نمایش داده نمی‌شود.
- پرونده‌های مرتبط: `src/utils/demand-response-context.ts`، `src/components/DemandWorkspace.tsx`، `tests/demand-response-context.test.ts` و `tests/demand-workspace-races.test.ts`.
- **شواهد واقعی scoped:** فایل‌های منبع در Sandbox ایزوله با `git hash-object` و SHA دقیق GitHub برابر شدند؛ strict TypeScript برای helperها و تایپ‌ها و ۱۹/۱۹ آزمون واقعی Vitest (۱۰ قدیمی + ۷ جدید) موفق بود. اجرای scoped لزوماً تضمین `bun run qa:full`، مرورگر و سرور عملیاتی نیست. هیچ دادهٔ واقعی، VPS یا مخزن شرکت تغییر نکرد.

- **ایمنی قطع ارتباط حین بازخوانی:** آغاز هر refresh پیش از هر `await`، کلید اعتبار جزئیات را نامعتبر و epoch تأییدیهٔ ذخیره را باطل می‌کند. اگر دریافت فهرست شکست بخورد، جواب قبلی هرگز همچنان قابل ویرایش یا ذخیره نیست. تست یازدهم مسابقه‌های ناهم‌زمان، ترتیب invalidation پیش از network را بررسی می‌کند.

## سخت‌گیری نهایی برای گزارش مدیر و بارگذاری مجدد چارت (۲۰۲۶/۱۰/۲۶)

- پس از آغاز بازخوانی، پاسخ و گزارش قبلی بلافاصله در حالت نامعتبر قرار می‌گیرند؛ همین بازخوانی epoch تأیید ذخیره و epoch خروجی CSV را هم باطل می‌کند. در خطای شبکه دکمهٔ پاسخ‌دادن با دیتای قدیمی فعال نمی‌ماند.
- روابط درسی هنگام بازخوانی *همان چارت* هم با `loadedChartRevision` مجدداً بررسی می‌شوند. شناسهٔ چارت یکسان به‌تنهایی برای معتبر دانستن اطلاعات نسخهٔ قدیمی کافی نیست؛ قبل از پایان دریافت، UI می‌گوید روابط هنوز بارگذاری نشده‌اند.
- خروجی **محرمانهٔ CSV ریز دانشجو** فقط بعد از بارگیری موفق گزارش مجاز است. تأیید دانلودِ دیررس اگر کاربر فرم/حساب/دامنه دسترسی را تغییر دهد نادیده گرفته می‌شود و هیچ `Blob` یا فایل دانلودی ایجاد نمی‌کند. زمان آزادسازی `Blob URL` کمی به‌تعویق افتاده تا مرورگرهایی مانند Safari فرصت آغاز دانلود داشته باشند. کنترل مجوز واقعی همچنان بر عهدهٔ سرور است.
- **شواهد:** تست‌های محدود در Sandbox با Vitest واقعی **۱۹/۱۹** پاس و strict TypeScript helper/انواع نیز پاس؛ TSX تغییرکرده با TypeScript `transpileModule` بدون خطای syntax کامپایل شد. Blobهای دقیق بررسی‌شده با SHA گیت‌هاب تطبیق داشتند. هنوز **full-app tsc, full qa:full, browser testing, merge و انتشار اصلی** ادعا نمی‌شود.

## گیت جامع روی منبع دقیق، رفع اشکال TypeScript (۲۰۲۶/۱۰/۲۶)

برخلاف آزمون‌های محدود قبلی، تمام ۲۸۶ Blob مخزن روی SHA پایهٔ `707fc8368a4bbc70a7db1e80d4155b030b5fd8f7` در Sandbox مجزا با `git hash-object` تطبیق داده شدند. نخستین اجرای QA کامل یک نقص مستقل از نیازسنجی کشف کرد: بسته‌های تایپ React در `package.json` و `bun.lock` ثبت نشده بودند؛ سه خطای TypeScript در `AppErrorBoundary` و یک خطای تست مربوط به constructor تولید می‌شد. با افزودن نسخه‌های قفل‌شدهٔ `@types/react@19.3.0` و `@types/react-dom@19.3.0`، اجرای بعدی `bun run qa:full` با **exit 0** و **۲۷۸/۲۷۸ تست در ۵۰ فایل**، چک TypeScript، بیلد کامل افزونه/فرانت/Express و smoke API مصنوعی موفق شد.
