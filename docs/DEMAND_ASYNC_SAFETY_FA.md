# ایزوله‌سازی درخواست‌های ناهم‌زمان نیازسنجی و امنیت تغییر نقش

**تاریخ:** ۲۰۲۶/۱۰/۲۶  
**دامنه:** پنل نیازسنجی دانشجو و مدیر؛ فقط مخزن درس‌چین.  
**قانون:** اطلاعات دانشجویی و گزارش شخصی مدیر نباید به context جدید «منتقل» شوند یا توسط یک درخواست قدیمی بازنویسی شوند.

## باگ‌های کشف‌شده
1. پاسخ HTTP قدیمیِ فهرست فرم‌ها ممکن بود بعد از درخواست جدید برسد و فهرست/انتخاب فرم و گزارش مرتبط را قدیمی کند.
2. جابه‌جایی بین فرم‌ها ممکن بود تا دریافت پاسخ جدید، انتخاب‌های دانشجو یا آمار فرم قبلی را روی صفحه نگه دارد.
3. تغییر چارت ممکن بود روابط پیش‌نیاز متعلق به چارت قبلی را برای چارت جدید معتبر نشان دهد.
4. **مرز هویت/نقش**: اجرای پاک‌سازی در `useEffect` بعد از نخستین render است؛ تغییر نقش، شناسهٔ حساب یا مجوز/محدودهٔ مدیریتی باید *پیش از نخستین render فضای کاری* آن را از نو mount کند.
5. هنگام بازنشانی نقش، پیش‌فرض انتخاب ترم و چارت نباید از مقدار stale محبوس در closure تابع refresh پیروی کند.

## قرارداد اجرایی
- `createRequestEpoch()` تمام refreshهای قدیمی را بعد از آغاز refresh جدید یا unmount نامعتبر می‌کند.
- در جابه‌جایی فرم، علاوه بر پاک‌سازی effect، کلید `demandDetailKey(role, surveyId, revision)` **در همان render** بررسی می‌شود؛ فقط پاسخ با کلید settled یکسان و وضعیت `ready` اجازهٔ نمایش گزارش، انتخاب درس، شماره دانشجویی و خوداظهاری ترم آخر را می‌دهد. در غیر این صورت فقط وضعیت بارگذاری/خطا و فرم غیرفعال نمایش داده می‌شوند.
- بارگذاری ناموفق detail حالت `error` و کنترل retry دارد و ذخیرهٔ پاسخ بدون detail موفق مجاز نیست.
- شناسهٔ چارت بارگذاری‌شده با شناسهٔ چارت مورد نیاز برابر باشد؛ در غیر این صورت فهرست شروط معتبر شناخته نمی‌شود.
- پوستهٔ `DemandWorkspace` با کلید مبتنی بر role، user ID، roles، permissions و demandScopes، component داخلی را **با تغییر principal از نو mount** می‌کند. این کار جایگزین مجوزسنجی سرور نیست.
- پاک‌سازی role، تمام draft، شماره دانشجویی، وضعیت ترم آخر و آمار/چارت قدیمی را صفر می‌کند؛ `refresh(true)` پس از پاک‌سازی، ترم و چارت پیش‌فرض را از دادهٔ جدید بازمی‌یابد.
- سیاست‌های دانشگاه، اطلاعات اکانت واقعی، API permission checks، محیط استقرار و مخزن تکین تغییر نمی‌کنند.

## شواهد و محدودیت
- روی **فایل‌های متن دقیق دریافت‌شده از GitHub** در محیط ایزولهٔ Vercel Sandbox با Vitest واقعی، `tests/demand-workspace-races.test.ts` با **۱۰/۱۰ آزمون موفق** اجرا شد (۶ آزمون اولیه + ۲ مرزبندی هویت/پاک‌سازی پیش‌فرض‌ها + ۲ آزمون جدید key معتبر فرم در render). رفتار تابع `isCurrentDemandDetail` برای تعویض فرم، role، revision و حالت خطا به‌صورت واقعی اجرا شد؛ آزمون UI/مرورگر کامل هنوز باقی است.
- TSX فایل تغییرکرده با TypeScript `transpileModule` بدون خطای نحوی تبدیل شد. این **جایگزین `tsc` جامع یا تست تعامل واقعی مرورگر نیست**.
- برای ادغام: اجرای `bun run qa:full` روی SHA همین شاخه، بررسی مرورگری تغییر نقش سریع، بازگشت آفلاین/خطای شبکه، اصلاح احتمالی ترم/چارت با دادهٔ واقعی فقط در محیط مجاز و عدم مخلوط شدن دادهٔ مدیر/دانشجو لازم است.
- دامنهٔ Preview Vercel با سقف انتشار روزانه مواجه شد؛ این تغییر ادعای deploy جدید یا VPS ندارد.

## راهنمای تست دستی با دادهٔ ساختگی
1. در دموی دانشجو نیازسنجی اول را انتخاب کن، پاسخ را ببین و بلافاصله فرم دوم را انتخاب کن. پیش از جواب API دوم، پاسخ اول نباید قابل ذخیره یا نشان‌داده‌شدن به‌عنوان جواب فرم دوم باشد.
2. در نقش مدیر بین دو گزارش سریع جابه‌جا شو؛ گزارش و نمودار فرم اول نباید روی فرم دوم باقی بماند.
3. نقش مدیر/دانشجو و هویت آزمایشی را تغییر بده؛ فرم‌ها، شماره دانشجویی، دروس انتخابی و آمار سابق نباید حتی به‌طور موقت زیر هویت جدید ظاهر شوند.
4. ارتباط را قطع کن: وضعیت خطا و retry، بدون فعال شدن دکمهٔ ذخیره با دادهٔ مانده از فرم قدیمی.
