# P0 — ابطال نشست‌های قدیمی پس از تغییر یا بازیابی رمز عبور

**تاریخ:** ۱۴۰۵/۰۸/۰۶ (۲۰۲۶/۱۰/۲۸)  
**دامنه:** فقط ریپوی `mohammadrezamie/DarsChin`، بدون تغییر VPS یا سایر مخازن.

## ایراد تأییدشده

در نسخهٔ پیشین `server/middleware/auth.ts` توکن‌های JWT تا هفت روز اعتبار داشتند و تنها امضا/انقضا و وجود کاربر بررسی می‌شد. تغییر رمز با `/api/auth/change-password` و بازیابی با OTP از طریق `/api/auth/recover-password` رمز ذخیره‌شده را تغییر می‌داد، اما **JWT دزدیده‌شدهٔ قبلی همچنان مجاز بود**. برای استفادهٔ واقعی دانشجویان این ریسک قابل قبول نیست.

## رفتار جدید

- فیلد اختیاری `User.sessionVersion` در JSON ذخیره می‌شود. نسخهٔ غایب در داده‌های قدیمی معادل صفر است.
- تولید JWT، `sv` را از **رکورد معتبر همان کاربر در دیتابیس** می‌گیرد، نه از دادهٔ دلخواه درخواست.
- Middleware هر درخواست احرازشده را در مقابل نسخهٔ ذخیره‌شده کنترل می‌کند؛ مقدار `sv` دست‌کاری‌شده، نامعتبر یا متفاوت، **401** است.
- هنگام تغییر موفق رمز، نسخه افزایش می‌یابد و **پس از ذخیرهٔ دیتابیس**، توکن تازه در پاسخ داده می‌شود. `AuthContext` مرورگر فعلی را با همان توکن به‌روز نگه می‌دارد؛ سایر دستگاه‌ها و توکن‌های قدیمی بسته می‌شوند.
- هنگام بازیابی با OTP معتبر، افزایش نسخه همهٔ نشست‌های قبلی را باطل می‌کند؛ کاربر باید با رمز جدید وارد شود. OTP یک‌بارمصرف باقی می‌ماند.
- JWTهای قدیمیِ فاقد `sv` تنها **تا نخستین تغییر رمز** برای حساب‌هایی با نسخهٔ صفر معتبرند. پس از نخستین تعویض، حتی توکن قدیمی بدون `sv` دیگر معتبر نیست. این سازگاری، اجبار به خروج ناگهانی تمام کاربران صرفاً در زمان انتشار را برطرف می‌کند.

## آزمون‌های واقعی

- فایل `tests/auth-session-revocation.test.ts` سه آزمون API با `express`/`supertest` دارد: تغییر رمز و صدور توکن جدید، بازیابی OTP و رد تکرار، و رد توکن جعلی/قدیمی بعد از نخستین rotation.
- Vercel Sandbox ایزوله با **کد تطبیق‌داده‌شده با SHA ریپو**: `bun run qa:full` با نصب frozen lock، TypeScript، **۶۰ فایل و ۳۲۷ تست Vitest**، بیلد React/Vite/Express/افزونه و API smoke مصنوعی **exit 0**.
- **۳۰۱ فایل غیر‌باینری با Git blob SHA برابر شدند**. فایل‌های باینری/ZIP در این ممیزی متنی ادعا نشده‌اند.
- تست دستی با سخت‌افزار iPhone/Safari و تأیید انتشار روی VPS انجام نشده و پیش‌نیاز پذیرش عملیاتی باقی است.

## محدودیت‌ها و اقدامات باقی‌مانده

- خروج عادی `/api/auth/logout` همچنان **حذف محلی توکن** است، نه لیست ابطال مستقل هر دستگاه. برای «خروج از همهٔ دستگاه‌ها» می‌توان API آگاهانهٔ افزایش نسخهٔ نشست را به‌صورت قابلیت جدا اضافه کرد. این PR عمداً رفتار کلی logout را تغییر نمی‌دهد.
- `sessionVersion` در دیتابیس JSON فقط برای **تک‌فرایند** معتبر است؛ برای مقیاس چند instance باید دیتابیس تراکنشی مشترک و سیاست مدیریت session/refresh token طراحی شود.
- حفاظت در برابر سرقت توکن همچنان نیازمند TLS، جلوگیری از XSS، کنترل ذخیره‌سازی مرورگر و حداقل‌سازی زمان اعتبار JWT است. باطل‌شدن پس از تغییر رمز به تنهایی امنیت کامل حساب را تضمین نمی‌کند.
- خطاهای پایگاه داده، صحت پیامک واقعی، خطای VPS، استقرار و مسیر proxy مستقل بررسی می‌شوند. هیچ دادهٔ واقعی، کلید خصوصی یا مخزن دیگری تغییر نکرد.

**معیار پذیرش:** پس از تغییر یا بازیابی رمز، یک درخواست واقعی با توکن قبلی باید 401 باشد؛ بعد از تغییر رمز توکن تازهٔ همین مرورگر باید 200 بگیرد؛ بعد از بازیابی نیز ورود دوباره لازم است.
