# P0 — ضدسوءاستفادهٔ API عمومی و تشخیص قطعی شکست راه‌اندازی

تاریخ: ۲۰۲۶/۱۰/۲۶  
دامنه: **فقط درس‌چین**؛ بدون تغییر در VPS، Nginx، دادهٔ کاربران، مخازن دیگر یا سرویس تکین.

## چرا این تغییر؟

CAPTCHA محلی و Cloudflare Turnstile جلوی پاسخ بدون چالش را می‌گیرند، ولی به‌تنهایی جلوی سیل درخواست ایجاد CAPTCHA یا ارسال موازی به API را نمی‌گیرند. ورود ناموفق به تفکیک شمارهٔ همراه و ارسال OTP به تفکیک شماره محدود بودند، اما نیاز به دفاعِ لایهٔ عمومی در برابر درخواست‌های زیاد از یک اتصال داشتیم.

خطای دیگری هم در `server.ts` وجود داشت: وقتی `startServer()` Promise را رد می‌کرد، خطا لاگ می‌شد اما `process.exitCode` الزاماً ناموفق نبود. هنگام سرویس systemd و استقرار، خروج با کد موفق **نباید** نشانهٔ یک راه‌اندازی سالم جلوه کند.

## رفتار پیاده‌شده

کتابخانهٔ تثبیت‌شدهٔ `express-rate-limit@8.7.1` با `bun.lock` دقیق به پروژه اضافه شده. محدودیت‌های اولیه **برای یک فرایند سرور** به‌ترتیب زیر هستند:

| عملیات عمومی | محدودیت از یک IP / شبکهٔ IPv6 | بازهٔ پنجره |
| --- | --- | --- |
| صدور CAPTCHA تصویری | ۲۴۰ درخواست | ۵ دقیقه |
| تلاش ورود | ۹۰ درخواست | ۱۵ دقیقه |
| ثبت‌نام | ۸۰ درخواست | یک ساعت |
| درخواست ارسال OTP | ۶۰ درخواست | ۱۵ دقیقه |

- عبور از سهمیه: HTTP **429**، پاسخ JSON واضح، `Retry-After` و هدر استاندارد `RateLimit`. پاسخ خطا کش نمی‌شود.
- هر مسیر سهمیهٔ مستقل دارد. مسیر سلامت، مسیرهای کاربر واردشده و صفحات استاتیک مشمول این سهمیه‌های **مهمان** نیستند.
- در production فقط `trust proxy = loopback` مجاز است تا Nginx محلی بتواند IP کاربر را منتقل کند؛ تنظیم ناامن `true` استفاده نمی‌شود. **Nginx باید هدرهای Forwarded را درست و معتبر تعیین کند.** ورودی‌های جعلیِ سمت چپ `X-Forwarded-For` در تست با وجود IP واقعی ثابت نتوانستند سقف را دور بزنند.
- آدرس‌های IPv6 به‌صورت شبکهٔ `/56` شمارش می‌شوند تا عوض‌کردن انتهای آدرس راه دور زدن آسان نباشد.
- این اعداد **تضمین مناسب‌بودن برای دانشگاه/CGNAT نیستند**. IP مشترک ده‌ها دانشجو می‌تواند به 429 برسد. قبل از آغاز عمومی، بار واقعی، پهنای شبکه و تجربهٔ دانشگاهی باید سنجیده و سهمیه‌ها پس از شواهد تنظیم شوند.

## کنترل شکست بوت

- هر خطای ردشدهٔ `startServer()` کد خروج **۱** را ثبت می‌کند. مثال کنترل‌شده: `PORT=invalid-port` در سرور ایزوله باید بدون listener و با `exit=1` تمام شود.
- این اصلاح **علت حادثهٔ واقعی VPS را شناسایی یا رفع نکرده**؛ برای آن همچنان `journalctl`، Permission و وضعیت `darschyn.service` بدون انتشار رازهای سیستم لازم است.
- تنها `systemctl active` + listener درست + `/api/health` صحیح و SHA یکسان و پایدار، معیار پایان حادثه است؛ به خروج موفق installer اعتماد نکنید.

## تست و شرط انتشار

- `tests/guest-abuse.test.ts`: محدودیت، `Retry-After`، مقابله با تزریق `X-Forwarded-For`، گروه‌بندی IPv6، جدابودن health و محدودسازی OTP.
- `scripts/smoke-api.cjs`: پس از smoke واقعی Express با حساب ساختگی و پایگاه‌دادهٔ disposable، فرایند معیوب با PORT نامعتبر جداگانه اجرا می‌شود و **exit=1** آزموده می‌شود.
- اجرای ایزوله با Bun lock منطبق با GitHub، TypeScript و همهٔ Vitest/Build/API smoke شرط مرج است. **هیچ تستی روی سرور اصلی یا شمارهٔ دانشجوی واقعی اجرا نشده است.**

## موانع حل‌نشده برای مقیاس و عرضه

1. MemoryStore این rate limiter بین Node workerها، چند سرور و بعد از restart مشترک/پایدار نیست؛ برای چند instance، Redis یا store مشترک معتبر و rate-limit در Edge/Nginx لازم است.
2. CAPTCHA محلی در JSON تک‌فرایندی مصرف می‌شود؛ برای چند instance/توزیع، مصرف اتمیک و TTL در store مشترک ضروری است.
3. ثبت‌نام امروز تأیید مالکیت شمارهٔ همراه را الزام نمی‌کند؛ **قبل از دعوت عمومی دانشجو** ثبت‌نام تأییدشده یا کنترل ضدحساب جعلی، SMS واقعی، حدود تلاش و سیاست حریم خصوصی باید تصمیم‌گیری و تست شوند.
4. دسترس‌پذیری جایگزین برای کپچای تصویری و آزمون ایران/آیفون هنوز باقی است. این PR جایگزین عملیات استقرار روی VPS نیست.
5. بررسی و آزمون تنظیم واقعی reverse proxy حتماً در سرور مستقلی از پروژهٔ تکین و پس از مجوز مالک انجام شود.

**مرز قطعی:** فقط مخزن `mohammadrezamie/DarsChin` و Sandbox موقتی QA تغییر کردند؛ ریپوی تکین و سایر مخازن صرفاً خواندنی‌اند.
