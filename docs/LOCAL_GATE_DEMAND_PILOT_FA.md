# Local Gate و معیار پذیرش پایلوت نیازسنجی درس‌چین

> ثبت اجرایی تصمیم‌های مالک [OWN-002، OWN-003، OWN-004 تا OWN-010 و OWN-020](OWNER_DECISIONS_FA.md)، ۲۰۲۶/۱۰/۲۵. اولویت **کیفیت، حریم خصوصی و قابلیت استفادهٔ واقعی** مقدم بر شتاب توسعه است. **قابل ساخت بودن فرانت‌اند یا Vercel READY، به معنی قابل فروش بودن محصول نیست.**

## ۱. الگوی اقتباس و استقلال کامل از تکین

اسکریپت `scripts/local-gate.sh` و مستند `docs/operations/CI_BUDGET_FA.md` در `mohammadrezamie/tnacompany` فقط **READ-ONLY** بررسی شدند. هیچ تغییر یا اجرایی در مخزن/سرور تکین صورت نمی‌گیرد. این الگو برای TypeScript/React/Express و قفل وابستگی Bun در درس‌چین بازنویسی شده؛ اسکریپت PHP/Laravel کپی نشده است.

فایل‌ها:
- `scripts/local-gate.cjs`: گیت چندحالتهٔ محلی و ایزوله؛ تست بدون تکیه بر سهمیهٔ GitHub Actions.
- `scripts/browser-mobile-qa.cjs`: مرور واقعی با Chromium برای عرض‌های ۳۲۰، ۳۹۰، ۴۳۰، ۷۶۸، ۱۰۲۴ و ۱۲۸۰ پیکسل؛ کنترل بیرون‌زدگی تداخل‌سنج لندینگ. به Playwright/Chromium **نصب‌شده در ماشین توسعه** نیاز دارد.
- `scripts/verify.cjs` و `scripts/smoke-api.cjs` ابزارهای موجود پروژه‌اند؛ اسکریپت جدید به جای تکثیر منطق، از روندهای معتبر خود پروژه استفاده می‌کند.

## ۲. فرمان‌های پیش از ادغام

در **ماشین توسعهٔ جدا از production** با Node 22+ و Bun و وابستگی‌های پروژه:

```bash
node scripts/local-gate.cjs --quick
node scripts/local-gate.cjs --quick --spec tests/course-demand-api.test.ts
node scripts/local-gate.cjs --full
node scripts/local-gate.cjs --browser
```

- `--quick`: ساختار مخزن + TypeScript + Vitest؛ گزینه `--spec` فقط در این حالت پذیرفته می‌شود.
- `--full` یا بدون آرگومان: `bun install --frozen-lockfile`، نظم مخزن، `tsc`، **همهٔ** تست‌های Vitest، ساخت خروجی و **smoke واقعی Express** با راه‌اندازی مجدد و دیتای موقت.
- `--browser`: حالت کامل همراه با Chromium و اندازه‌گیری DOM در عرض‌های موبایل/تبلت/دسکتاپ.
- `--browser-only`: فقط QA مرورگر روی build موجود؛ **جایگزین full gate برای ادغام نیست**.

برای تست مرورگر، Playwright و فایل اجرایی Chromium را در محیط توسعه به‌صورت **محلی و بدون ثبت lock جدید** تهیه کنید؛ گیت اگر نصب نباشد **fail closed** می‌کند و تست مرورگر را وانمود نمی‌کند. اسکریپت به‌صورت پیش‌فرض هیچ پکیج خارجی را در production دانلود نمی‌کند.

**خطرات کنترل‌شده:** تولید `DARSCHYN_DATA_DIR` موقت و کلید/اعتبارنامهٔ مصنوعی، حذف اطلاعات حساس محیط پیامکی، ممنوعیت اجرا با `NODE_ENV=production` یا مسیر `/var/www` و پاک‌سازی فایل‌های موقت حتی در شکست. با این حال بازبین باید پیش از شروع تست تأیید کند در مسیر واقعی production نیست. گیت **هیچ ادغام خودکاری انجام نمی‌دهد**؛ خودکارسازی merge فقط بعد از افزودن سازوکار قابل ممیزیِ SHA-محور و تأیید صریح مالک مجاز است.

## ۳. معیار پذیرش نیازسنجی اول — پیش از فروش/انتشار

1. مدیر دارای دامنهٔ مجوز درست، برای یک/چند/همهٔ ورودی‌های همان واحد، رشته و مقطع، پیش‌نویس بسازد؛ **یک چارت معتبر برای هر ورودی** و فهرست دروس متناسب با همان ورودی تضمین شود.
2. تا مدیر نیازسنجی را `OPEN` نکرده، دانشجو آن را برای پاسخ نبیند؛ پس از `CLOSED` هیچ پاسخ جدید/ویرایش پذیرفته نشود؛ تاریخچه حفظ شود.
3. دانشجوی یک ورودی، **حتی با POST دستی** نتواند درس نامربوط به چارت خودش درخواست کند. گرایش انتخاب‌نشده مانع دیدن نیازسنجی عمومی نباشد؛ منطق اختیاری گرایشِ دیگر تا تأیید قوانین آموزشی منع خودکار نشود.
4. یک پاسخ یکتا برای هر دانشجو/نیازسنجی؛ ویرایش تعداد آرا را دوبرابر نکند. ذخیره و بازیابی پس از ری‌استارت سرور و بکاپ/بازگردانی **آزمایش عملی** شوند.
5. مدیر گروه در سطح کلی، ورودی، درس و اعلام احتمال فارغ‌التحصیلی آمار ببیند. **در گزارش فردی**، با مجوز اضافی `demand.export` و scope معتبر، نام/شماره دانشجویی، ورودی، اختیاری‌بودن گرایش، همهٔ دروس انتخابی، زمان و اظهار فارغ‌التحصیلی را بررسی/فیلتر کند؛ مشاهده و خروجی ثبت حسابرسی شود.
6. کسی که فقط `demand.manage` دارد به نام/شماره/انتخاب‌های فردی دسترسی نداشته باشد. فایل CSV ضد formula injection و قابل بازشدن با فارسی صحیح در Excel باشد. خروجی دانشجویانی که هیچ درسی انتخاب نکرده‌اند نیز بررسی شود.
7. سناریوهای حداقل دو ورودی با **چارت متفاوت**، دانشجوی ترم آخر (صرفاً خوداظهاری)، دانشجوی بی‌گرایش، پاسخ صفر درس، تغییر انتخاب، دسترسی خارج از scope، REST نامعتبر و CSV به‌صورت تست اجرایی پوشش داده شوند.
8. گیت کامل + مرورگر با موبایل ۳۲۰/۳۹۰/۴۳۰ + دسکتاپ + حالت تاریک/روشن، **بر همان SHA نهایی** پاس شود؛ یک تست واقعی روی Safari iPhone نیز جداگانه لازم است. Vercel ممکن است فقط فرانت‌اند را ارائه دهد؛ API واقعی باید در استیجینگ ایزوله تأیید شود.
9. پیش از انتشار واقعی، پشتیبانی، شرایط استفاده، حفاظت دادهٔ دانشجویی، کنترل abuse/CAPTCHA فرم‌های مهمان، نظارت/هشدار خطا و رویهٔ rollback/backup احراز شوند.
10. قوانین پروژه و کارآموزی، شرط حداقل واحدهای گذرانده‌شده، سقف‌ها و استثناها **تا تکمیل پرسش‌وپاسخ با مالک و مصوبهٔ مرتبط** نباید با نتیجهٔ «مجاز قطعی» به دانشجو نمایش داده شوند.
