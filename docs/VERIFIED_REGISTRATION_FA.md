# P0 — تأیید مالکیت شمارهٔ موبایل هنگام ثبت‌نام واقعی

**ثبت در GitHub:** ۲۷ اکتبر ۲۰۲۶  
**محدوده:** فقط مخزن درس‌چین؛ هیچ سرویس تولید، مخزن تکین، پنل SMS واقعی یا DNS تغییر نکرده است.

## انگیزه

CAPTCHA لزوماً ثابت نمی‌کند که دانشجو مالک شمارهٔ موبایل واردشده است. در نسخهٔ قبلی، یک نفر می‌توانست شمارهٔ دیگری را وارد کند و رمز تعیین کند. این ویژگی پیش از پذیرش ثبت‌نام عمومی باید با OTP واقعی و تأیید سمت سرور حل شود.

## جریان جدید

این ویژگی با `DARSCHYN_REGISTRATION_OTP_REQUIRED=true` فعال می‌شود؛ در محیط‌های آزمایشی می‌توان آن را موقتاً `false` گذاشت تا ورود دانشجوی دمو بدون ارسال پیامک باقی بماند، اما **false برای ثبت‌نام عمومی تأییدشده نیست**.

1. فرم ثبت‌نام از `GET /api/security/challenge` تنظیمات عمومی `registrationOtpRequired` را می‌خواند؛ در صورت خطا فرم را بی‌صدا دور نمی‌زند.
2. در حالت فعال، کاربر ابتدا شماره و CAPTCHA با اقدام `otp` را حل می‌کند و از `POST /api/auth/otp/send` با `purpose=registration` یک چالش مخصوص همان شماره می‌گیرد. برای شمارهٔ قبلاً ثبت‌شده، درخواست رد می‌شود.
3. OTP شش‌رقمی فقط **دو دقیقه** اعتبار دارد؛ هش bcrypt آن در پایگاه دادهٔ موقتی ثبت می‌شود و جواب خام به مرورگر نمی‌رسد. درخواست‌های زیادی از یک اتصال و دفعات مجاز تلاش با گیت‌های موجود محدودند.
4. کاربر کد پیامک، نام، رمز و CAPTCHA مجزای اقدام `register` را وارد می‌کند. سرور OTP را فقط در صورتی که `id + mobile + purpose=registration + code + expiry` مطابقت داشته باشند قبول می‌کند.
5. OTP همراه ایجاد حساب جدید یک‌بار مصرف می‌شود؛ زمان `mobileVerifiedAt` تنها وقتی ثبت می‌شود که این مرحله واقعاً پاس شده باشد. OTP ورود یا بازیابی نمی‌تواند جای OTP ثبت‌نام مصرف شود و endpoint عمومی `/otp/verify` کد ثبت‌نام را مصرف نمی‌کند.
6. در خطای ارسال SMS، timeout، کد منقضی یا پیکربندی نامعتبر، ثبت‌نام امن متوقف می‌ماند و پیام روشن به کاربر می‌دهد. پس از تغییر شماره، OTP قبلی در UI قابل استفاده نیست. دمو بدون flag از مسیر ثبت‌نام موجود استفاده می‌کند و به‌اشتباه `mobileVerifiedAt` دریافت نمی‌کند.

## گیت اصلی پیامک / تولید واقعی

- `SMS_PROVIDER=niazpardaz` و فرستنده، API key اختصاصی درس‌چین، الگوی مورد تأیید سرویس‌دهنده و `NIAZPARDAZ_SMS_OTP_APPROVED=true` باید واقعاً بررسی و در secret store پروژه تنظیم شده باشند. از هیچ کلید یا رمز دیگرِ ریپوها استفاده نکنید.
- `SMS_PROVIDER=log` در `NODE_ENV=production` **تحویل واقعی پیامک نیست** و باید ۵۰۳ برگرداند. حالت آزمایشی با رمز OTP ساختگی فقط در تست ایزوله مجاز است.
- نمونه تنظیمات `deploy/.env.vps.example` و `deploy/.env.staging.example` حاوی flag صریح false به‌عنوان حالت پیش از راه‌اندازی‌اند. قبل از عمومی‌شدن سامانه این وضعیت باید با تست ارسال/دریافت واقعی و انتخاب صریح مالک به true تغییر کند.
- محیط تعاملی Vercel بدون Express نمی‌تواند تأییدیهٔ واقعی صادر کند. API همان‌مبدأ و TLS نیز قبل از انتشار لازم‌اند.

## برنامهٔ تست

- پوشش `tests/verified-mobile-registration.test.ts`: بدون OTP، کد اشتباه، عدم تطبیق شماره، انقضا، مصرف دوباره، جلوگیری از مصرف از طریق endpoint دیگر، log-mode غیرفعال production و سازگاری با مسیر دمو.
- گیت کامل: `bun run qa:full` همراه نصب frozen-lock، TypeScript، Vitest، بیلد فرانت/بک/افزونه و API smoke روی دیتابیس ساختگی.
- آزمون مرورگری در چند اندازه با حالت OTP فعال و غیرفعال، خطای شبکه و برگشت به فرم قبلی لازم است. **تست نرم‌افزاری ارسال SMS به معنی ارسال واقعی نیست**.

## محدودیت‌های شفاف

- این نسخه هنوز یک JSON datastore تک‌فرایندی با چالش‌های موقتی است؛ برای چند instance مصرف اتمیک و shared store/transactional DB لازم خواهد بود.
- anti-abuse موجود IPمحور است؛ نرخ‌های شبکهٔ دانشگاه یا پشت CGNAT باید پس از تست واقعی تنظیم شوند.
- بدون ارسال واقعی SMS و پذیرش دامنه/خدمات VPS، قابلیت «ورود دانشجوی واقعی» تأییدشده محسوب نمی‌شود. این تغییر مجوز اجرای deploy یا ویرایش مخزن دیگری نیست.

**اصل غیرقابل نقض:** فقط `mohammadrezamie/DarsChin` قابل نوشتن است و هیچ آزمونی از شماره یا رمز واقعی استفاده نمی‌کند.

## شواهد اجرای QA روی شاخه (۲۰۲۶/۱۰/۲۷)

- **گیت کامل واقعی:** Vercel Sandbox ایزوله با منبع اصلیِ DarsChin و `bun install --frozen-lockfile`، `bun run qa:full`: **۵۷ فایل Vitest / ۳۱۵ تست PASS، TypeScript و build فرانت/Express/افزونه و API smoke PASS، exit 0**. باگ regex موبایل هنگام تست مرورگر کشف شد و پس از استخراج helper مشترک و افزودن سه تست جدید، گیت از ابتدا دوباره اجرا و پاس شد.
- **Chromium/Playwright:** فرم `/register` در ۳۲۰، ۳۶۰، ۳۹۰، ۴۳۰، ۷۶۸ و ۱۴۴۰ پیکسل، ورود به مرحلهٔ درخواست کد، نمایش فیلد SMS و CAPTCHA مرحلهٔ نهایی، برگشت به مرحلهٔ اول با تغییر شماره، بدون خطای JavaScript و بدون overflow افقی **۶/۶ PASS**. **پاسخ ارسال SMS برای این آزمون صرفاً mock مرورگری بوده است**؛ اعتبارسنجی سروری با کد هش‌شده و عمر/هدف محدود در تست‌های واقعی Vitest بررسی شده، نه با ارسال پیامک واقعی.
- **شفافیت وضعیت:** این شواهد مربوط به شاخه و Sandbox است، نه استقرار روی VPS یا تحویل پیامک توسط اپراتور. ادغام و آزمون پایداری بعدی باید با SHA همان شاخه ثبت شوند.
