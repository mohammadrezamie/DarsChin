## شیوهٔ استفاده و ثبت پیشرفت

- کادرهای `[ ]` **کارِ باز** هستند؛ هیچ دستیار نباید بدون مشاهدهٔ شواهد و تأیید کاربر تیک بزند یا ادعای اجرای عملیاتی کند.
- ابتدا موارد **P0 امنیت تاریخی و حساب GitHub**؛ سپس **P0 اعتبارنامه‌های افشاشده و نشست‌ها**؛ بعد **P1 استقرار جدید و تست میدانی**. برای جلوگیری از تداخل، قدم‌های هر بخش را به ترتیب انجام بده.
- اگر گزینه‌ای در GitHub موبایل پیدا نشد، از مرورگر گوشی گزینهٔ **Request Desktop Website / درخواست سایت دسکتاپ** را بزن و دوباره مسیر `Settings` را باز کن. برچسب گزینه‌ها ممکن است با UI و پلن تغییر کنند.
- پس از هر مورد، فقط مدرک **غیرحساس** نگه دار: نام تنظیم، وضعیت روشن/خاموش، تاریخ، شمارهٔ تیکت/PR و نتیجهٔ تست، نه مقدار توکن. اگر لازم شد، مالک صرفاً وضعیت را در گفت‌وگو تأیید کند تا سند در PR بعدی به‌روزرسانی شود.
- **قانون همیشگی:** به اتصال فعلی VPS به ریپو، تنظیمات سرور فعلی، ریپوی تکین و داده‌های واقعی دست نزنید. نصب تازه و حذف سرویس/دادهٔ قدیمی فقط در پروژهٔ استقرار جداگانه با اجازهٔ صریح و بکاپ.

## فاز ۱ — بستن مسیر آلودگی جدید در GitHub (P0، قبل از مشارکت دیگران)

### ۱.۱ ساخت Ruleset محافظ شاخهٔ main

- [ ] وارد حساب **مالک** GitHub در https://github.com/mohammadrezamie/DarsChin شو.
- [ ] روی `Settings` مخزن بزن (در گوشی شاید داخل منوی `...` یا حالت Desktop باشد).
- [ ] به `Rules → Rulesets` برو، `New ruleset → New branch ruleset` را بزن؛ نام پیشنهادی: `Protect main - mandatory CI`.
- [ ] `Enforcement status` را `Active` قرار بده، نه `Evaluate` یا `Disabled`.
- [ ] در `Target branches` دقیقاً `Default branch` یا `main` را انتخاب کن؛ روی تمامی شاخه‌ها یا PRهای درحال‌کار تصادفاً اعمال نکن.
- [ ] `Require a pull request before merging` را روشن کن. اگر بررسی‌کنندهٔ مستقل هنوز نداری، **الزام تعداد Approval** را طوری تنظیم کن که صاحب تنها مخزن قفل نشود؛ حفاظت تست نباید دور زده شود.
- [ ] `Require status checks to pass` را روشن و check واقعی **`Typecheck / Tests / Build`** را از یک Run سبز اخیر انتخاب کن؛ اسم check را دستی و اشتباه وارد نکن. **Require branches to be up to date before merging** اختیاری است؛ اگر باعث اجرای بی‌مورد Actions می‌شود، برای کم‌مصرف بودن CI ارزیابی و فقط در صورت نیاز فعال کن.
- [ ] `Block force pushes` و `Restrict deletions` را فعال کن؛ برای مدیر و اپ‌های دارای دسترسی، bypass عمومی/غیرضروری ایجاد نکن.
- [ ] `Create/Save ruleset` را بزن. در صفحهٔ قواعد بررسی کن نام قانون، وضعیت **Active** و target **main** دیده می‌شود.
- [ ] **تست پذیرش:** یک PR آزمایشی بی‌خطر از شاخهٔ جدا باز کن و بررسی کن قبل از سبز شدن check امکان Merge ندارد؛ امکان Push مستقیم بدون PR/Force Push به main نباید برای بازیگران غیرمجاز برقرار باشد. برای آزمودن قوانین **به main واقعی Force Push نکن**؛ از UI قواعد و رویدادهای PR شاهد بگیر.
- [ ] **مدرک پایان:** تاریخ و عنوان Ruleset، check دقیق و نتیجهٔ آزمون بدون عکس حاوی Secrets.

**وضعیت در آخرین بازرسی:** `GET /rulesets` آرایهٔ خالی برگرداند؛ API محافظت شاخه برای اتصال حاضر `403 Resource not accessible by integration` داد. این‌ها به معنی «تنظیم شده» نیستند.

### ۱.۲ اسکن و دریافت محرمانهٔ گزارش آسیب‌پذیری

- [ ] در همان ریپو به `Settings → Advanced Security` یا `Settings → Security & analysis / Code security and analysis` (بسته به رابط) برو.
- [ ] گزینهٔ **Secret scanning** را در صورت ارائه برای مخزن روشن کن؛ **Push protection** را هم برای جلوگیری از انتشار Secretهای جدید فعال کن. اگر فعال‌شدن هر کدام به تنظیم حساب/مالکیت یا پلن بستگی دارد، آن را به‌عنوان مانع با متن غیرحساس ثبت کن.
- [ ] **Dependabot alerts** و **Dependabot security updates** را بررسی و مطابق قابلیت حساب روشن کن. در خود سورس، `.github/dependabot.yml` PRهای هفتگی محدود برای Bun و GitHub Actions ایجاد می‌کند؛ این فایل به معنی روشن بودن تمام هشدارهای حساب نیست.
- [ ] بخش **Private vulnerability reporting** را فعال کن تا آسیب‌پذیری‌های واقعی به‌جای Issue عمومی در `Security → Advisories → Report a vulnerability` خصوصی گزارش شوند.
- [ ] در `Security` ریپو، هشدارهای **Secret scanning / Dependabot** را بدون کپی مقدار Secret بازبینی کن. اگر هشدار نشان‌دهندهٔ اعتبارنامهٔ معتبر است، اول مرحلهٔ چرخش فاز ۳ را اجرا کن.
- [ ] **تست پذیرش:** وضعیت هر گزینه را از صفحهٔ تنظیمات تأیید کن و در صورت امکان فرم گزارش خصوصی را **بدون ارسال گزارش ساختگی** باز کن.
- [ ] **مدرک پایان:** نام گزینه‌ها، وضعیت فعال، تاریخ و مواردی که UI ارائه نکرد.

> Repository: `mohammadrezamie/DarsChin`

The maintained default branch was reconstructed and no longer tracks the problematic runtime files, but old pull-request commits, cached diffs/views and refs may still expose historical content. Please guide us through identifying affected refs and removing cached sensitive content safely. Known old PRs for investigation include #27, #28, #29, #37, #42, #56 and #71; this list is not exhaustive. Please tell us which evidence, first-changed commit IDs or `git-filter-repo` output you need, and how to handle pull-request refs, release archives, forks and caches. - [ ] **تست پذیرش:** تأیید صریح Support از وضعیت refs/cached PR views؛ بررسی release assets، آرشیوها، forkهای شناخته‌شده و cloneهایی که خارج از کنترل GitHub‌اند. **حذف از main، Squash و پاک‌کردن Branch به‌تنهایی کافی نیستند.**

## فاز ۳ — چرخش/ابطال اعتبارنامه‌های احتمالیِ افشاشده (P0)

**این مرحله به حساب سرویس‌ها و محیط عملیاتی دسترسی می‌خواهد؛ با ابزار فعلی ChatGPT قابل تأیید نیست. رمز واقعی را در مخزن/چت قرار نده. اگر افشای زندهٔ کلید را تأیید کردی، ابطال فوری آن را بر کارهای کم‌اهمیت مقدم کن.**

- [ ] در یک جدول **خصوصی خارج از Git** فقط نام، محل استفاده، صاحب سرویس، آخرین وضعیت و تاریخ تعویض را بنویس: `ROOT_OWNER_PASSWORD`، `ROOT_OWNER_RECOVERY_KEY`، `JWT_SECRET`، API پیامک/OTP، Turnstile، GitHub PAT/SSH Deploy Key، توکن سرویس استقرار و هر کلید محیطی دیگری که در Git قدیمی دیده شده.
- [ ] هر اعتبارنامه‌ای که **واقعاً در تاریخچهٔ Public بوده و هنوز معتبر است** را افشاشده فرض کن؛ از پنل رسمی **صادرکنندهٔ همان کلید** revoke کن و کلید جدیدِ منحصر‌به‌فرد بساز. **نام کلید را نگه دار، نه مقدارش.**
- [ ] رمز Root و Recovery را قوی و مستقل انتخاب کن؛ JWT باید حداقل ۳۲ بایت تصادفی باشد و با هیچ رمز دیگری یکسان نباشد. کد Production با رمزهای پیش‌فرض یا `MOCK_OTP_CODE` شروع نمی‌شود.
- [ ] اگر `JWT_SECRET` فعلی افشا شده است، تعویض آن تمام JWTهای قبلی را نامعتبر می‌کند؛ برای خروج کاربران/اعلام اختلال ورود از پیش برنامه‌ریزی کن. اگر کلیدی با سرویس دیگری مشترک بوده، همان سرویس را نیز بررسی کن.
- [ ] توکن‌های مخزن، رمز SMS/OTP و Turnstile را از سرویس تولیدکنندهٔ هر کدام تعویض/ابطال کن؛ سپس مصرف‌کنندگان واقعی را در برنامهٔ استقرار تازه هماهنگ کن. **در این مرحله به اتصال قدیمی VPS به ریپو دست نزن.**
- [ ] در صورت احتمال افشای اطلاعات واقعی دانشجویان، دامنهٔ افشا، مسئول رسیدگی و الزامات قانونی اطلاع‌رسانی را **خصوصی** بررسی کن.
- [ ] **تست پذیرش:** سرویس مربوطه کلید قدیمی را دیگر قبول نکند؛ کلید جدید در محل امن کار کند؛ نشست‌های قدیمی در زمان مجاز باطل شده باشند.
- [ ] **مدرک پایان:** فقط تاریخ تعویض/ابطال، نام سرویس و نتیجهٔ آزمون، هرگز مقدار Secret.

## فاز ۴ — استقرار تازه و جدا از اتصال فعلی (P1، بعد از فازهای P0 و مجوز جداگانه)

- [ ] پیش از هر حذف، از دادهٔ ارزشمند فعلی یک بکاپ **رمزنگاری‌شده و خارج از Git** تهیه و قابلیت Restore آن را در محیط ایزوله امتحان کن.
- [ ] یک محیط staging مستقل از production، با Secretهای تازه و داده‌های صرفاً آزمایشی تعریف کن؛ GitHub connection قدیمی را تا تصمیم جداگانه نگه دار.
- [ ] `NODE_ENV=production`، HTTPS، DNS و reverse proxy صحیح، `HOST=127.0.0.1` برای Backend، عدم دسترسی مستقیم اینترنت به پورت برنامه، تنظیم CIDR و Trust Proxy، WAF/Rate Limit در لبه و لاگ بدون Secrets را بررسی کن.
- [ ] اول یک‌بار دیتابیس پایدار خارج از Git را با دسترسی حداقلی بساز؛ **پس از اولین بوت و آزمون Restore** `DARSCHYN_REQUIRE_EXISTING_DB=true` را فعال کن تا Mount مفقود به دیتابیس خالی تبدیل نشود. JSON DB تک‌پردازشی است؛ چند replica بدون مهاجرت تراکنشی فعال نکن.
- [ ] OTP ثبت‌نام با سرویس SMS واقعی، کپچای امن، مالکیت شمارهٔ موبایل، ابطال نشست، جداسازی دانشجو/مدیر و عدم نمایش بکاپ/اطلاعات افراد دیگر را در staging تست کن. Production نباید از OTP Mock یا کاربران Seed واقعی استفاده کند.
- [ ] روی SHA مشخص: `bun run verify`، `bun run smoke:api`، تست build، restart، Restore، مشاهدهٔ health و تست دستی موبایل/دسکتاپ و مسیرهای onboarding را اجرا کن. موفقیت Vercel Frontend به‌معنی درست‌بودن Backend نیست.
- [ ] روش Backup، مانیتورینگ، نسخه‌بندی Release، Rollback، CI کم‌مصرف و عدم Merge بدون تست را ثبت کن.
- [ ] **فقط پس از پذیرش کامل و اجازهٔ مالک** وضعیت اتصال قدیمی سرور/حذف نسخهٔ قبلی را تعیین کن؛ اجرای این تصمیم به هیچ دستیار خودکار واگذار نیست.

## پاسخ استاندارد دستیار وقتی مالک پرسید «حالا دقیقاً من چه کار کنم؟»

1. **اول** نسخهٔ این فایل، Issue #4 و Rulesets فعلی GitHub را بخوان و وضعیت «انجام شده/باز/نامعلوم» هر مورد را صریح و بدون حدس بگو.
2. **بعد** تنها مرحلهٔ بعدیِ انجام‌نشده را انتخاب و با مسیر دقیق UI (موبایل و دسکتاپ)، نام گزینه‌ها، مقادیر پیشنهادی، دکمهٔ Save و روش تأیید توضیح بده؛ اطلاعاتی که قبلاً تأیید شده دوباره از مالک نپرس.
3. وقتی مالک گفت مرحله را انجام داده، تا حد ابزار موجود آن را راستی‌آزمایی کن و فقط با **شاهد** بخش مربوط به آن را در سند با PR ثبت کن؛ اگر دسترسی نبود، «تأییدشده توسط مالک، راستی‌آزمایی مستقل نشده» ثبت کن.
4. سپس سراغ مرحلهٔ بعدی برو؛ همهٔ ۴ فاز را یک‌باره روی کاربر نریز مگر کاربر **فهرست کامل** خواسته باشد.
5. هیچ‌گاه به جای اقدام مالک در GitHub Support، Rotation یا VPS ادعای موفقیت نکن؛ تغییر سرور فعلی بدون مجوز صریح ممنوع است.

**معیار بسته‌شدن حادثه:** تنظیمات حفاظتی GitHub واقعاً فعال و آزمایش شده + تأیید پاک‌سازی متناسب از Support + تعویض/ابطال credentialهای در معرض خطر توسط صاحبان سرویس و مستندشدن ریسک‌های باقیمانده. **CI سبز به‌تنهایی برای خاتمه کافی نیست.**
