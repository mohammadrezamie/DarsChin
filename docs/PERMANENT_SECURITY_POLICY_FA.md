# منشور دائمی امنیت و توسعهٔ امن درس‌چین

**وضعیت: الزام دائمی P0 برای همهٔ مشارکت‌کنندگان، نگه‌داران، فورک‌ها و اپراتورهای استقرار — نسخهٔ ۱، ۱ نوامبر ۲۰۲۶**

> این سند قرارداد فنی برای تغییرات بعدی است، نه ادعای «امنیت کامل» یا گواهی ممیزی مستقل. وضعیت فعلی حادثهٔ عمومی‌شدن در [پروندهٔ پاسخ به حادثه](SECURITY_INCIDENT_RUNBOOK_20261101_FA.md) و [مسائل باز](https://github.com/mohammadrezamie/DarsChin/issues/4) ثبت می‌شود. سند باید پیش از هر PR خوانده شود و بدون بررسی پیامد امنیتی تضعیف نشود.

## ۱. اصول و محدوده

1. **سورس عمومی، داده خصوصی:** Public/MIT فقط به سورس مجوز می‌دهد؛ رمز، شماره و اطلاعات تحصیلی دانشجوی واقعی، دیتابیس، پیامک، خروجی اکسل، فایل لاگ، کلید API، JWT، Recovery Key، فایل ENV، اطلاعات VPS و زیرساخت مالک نباید در سورس، تست، Issue، PR، Artifact، Screenshot، Cache، Release یا مستندات انتشار یابند.
2. **اصل کمترین اختیار و انکار پیش‌فرض:** کاربر، مدیر واگذارشده، Root و مهمان در سمت سرور احراز هویت و مجوز مستقل دارند. مخفی‌کردن دکمه در React مجوز نیست. **Owner-only** فقط API را محدود می‌کند و جایگزین قواعد Reverse Proxy برای صفحات استاتیک نیست.
3. **جداسازی نصب‌ها:** Fork و self-hosting حق دسترسی به DB، دامنه، پیامک، فایل‌ها یا سرور نگه‌دارندهٔ اصلی را ندارند. هیچ deployment، backup، کلید، runner یا ENV تکین نباید از درس‌چین خوانده/تغییر داده شود. سرور فعلی بدون مجوز اپراتور دست‌نخورده می‌ماند.
4. **امنیت قابل‌سنجش:** هر ادعای رفع باگ باید به تست اجرایی SHA مشخص و وضعیت محدودیت‌ها متصل باشد. عبور CI ≠ امن‌بودن قطعی، سلامت استقرار یا پاک‌شدن آثار تاریخچه.

## ۲. قواعد اجباری توسعهٔ کد

### احراز هویت، مجوز و نشست

- هر endpoint مربوط به دانشجو/مدیر باید از `authenticate` و کنترل نقش/مجوز در **سرور** استفاده کند. برای دسترسی به رکوردها، صرف داشتن ID کافی نیست؛ مالکیت کاربر، محدودهٔ مجاز پردازش، ورودی، مقطع، رشته، واحد و نیمسال را بررسی کنید. آزمایش دسترسی متقابل دو دانشجو و Root/مدیر واگذارشده الزامی است.
- نقش `super-admin` فقط به شناسهٔ رزروشدهٔ `usr-super` **و** شمارهٔ ROOT تنظیم‌شده **و** نقش ذخیره‌شده وابسته است؛ هرگز از payload، localStorage، import، عنوان نقش یا شمارهٔ تصادفی Root نسازید.
- ورود/بازیابی رمز و OTP باید ضدّ enumeration، دارای سقف تلاش، CAPTCHA سمت سرور، انقضای معتبر و یک‌بارمصرف، هش رمز/Verifier و ابطال نشست بعد از تغییر credential باشد. هرگز به محیط production به دلیل نبود SMS یا کپچا مسیر fail-open ندهید.
- `JWT_SECRET` یکتا و قوی باشد؛ به توکن‌های دیگر سامانه‌ها، JWT امضاشده با کلید عمومی یا ورودی کاربر اعتماد نکنید. رمز، توکن و کلید در لاگ نیایند.

### داده، ذخیره و ورودی

- هر ورودی JSON/CSV/Excel/ZIP، query و نام فایل را با schema، حجم و تعداد مشخص validate کنید؛ از prototype pollution، path traversal، SSRF، اجرای کد غیرمعتمد و zip bomb پیشگیری کنید. ورودی خارجی فقط پس از بررسی و تأیید وارد کاتالوگ رسمی شود.
- ابتدا تغییرات حساس و audit را **یکپارچه** آماده کنید؛ سپس یک ذخیره‌سازی اتمیک. در شکست ذخیره، وضعیت حافظه باید به حالت قبلی بازگردد؛ پاسخ موفقیت یا دادهٔ ذخیره‌نشده ارسال نشود. هر restore با backup خصوصی تأییدشده، تست sandbox و rollback همراه باشد.
- دادهٔ ساختگی نباید با دیتای واقعی ادغام شود؛ `NODE_ENV=production` هرگز حساب دمو با رمز شناخته‌شده یا OTP mock را فعال نکند. دسترسی production به فایل دیتابیس از مسیر خارج Git و با مجوز حداقلی انجام شود. JSON Store فقط برای اجرای یک‌پردازشی مناسب است.
- پاسخ `500` نباید stack، مسیر سرور، `err.message` یا متن دادهٔ خصوصی را بازگرداند. اطلاعات حساب، پروفایل، کارنامه، تیکت، بکاپ، پیامک و هر پاسخ حساس `Cache-Control: no-store` داشته باشد. فایل‌ها و نماهای عمومی فقط اطلاعات انتشارپذیر را نشان دهند.

### فرانت‌اند و افزونه

- از `dangerouslySetInnerHTML`، `eval`، اسکریپت ثالثِ بدون بررسی، import URL ناشناس یا CSS/HTML ورودی کاربر استفاده نکنید. محتوای آموزشیار و پیام‌های کاربران را به‌صورت دادهٔ غیرقابل‌اجرا نمایش دهید.
- محتوای افزونه، دسترسی‌های `manifest`، `postMessage`، `chrome.storage` و ارتباط با API باید کم‌دسترسی و محدود به Origin و دادهٔ موردنیاز باشد. هیچ رمز آموزشیار یا حساب واقعی را ذخیره/ارسال/ثبت نکنید مگر با طرح مصوب و رضایت مشخص.
- PWA/Service Worker نباید پاسخ احراز هویت‌شده، JWT، API کاربر یا بکاپ را کش کند. از XSS، CSRF متناسب با مدل bearer/cookie، open redirect و injection محافظت کنید.

## ۳. مخزن و زنجیرهٔ تأمین

- **هر تغییر فقط روی شاخه‌ای مشتق از آخرین `main` تمیز** و با PR انجام شود؛ PR قدیمی و ref آلوده را بدون بررسی یا با history merge وارد `main` نکنید. ادغام squash نیز بدون بازبینی Tree و نتیجهٔ CI مجاز نیست.
- رمز، دادهٔ واقعی، `.env` و بستهٔ ZIP حاصل از runtime به Git نرود. پیش از هر PR: `bun run repo:public-check`، اسکن secrets و مراجعت به `SECURITY.md`. این اسکن فقط HEAD/امضاهای شناخته‌شده را پوشش می‌دهد و **جایگزین اسکن تمام تاریخچه نیست**.
- Dependencies جدید باید دلیل، سازنده/مجوز، زنجیرهٔ وابستگی و آسیب‌پذیری شناخته‌شده داشته باشند. `bun.lock` را حفظ کنید. GH Actions باید کم‌اختیار باشد (`permissions: contents: read` پیش‌فرض)، actionهای ثالث ترجیحاً به SHA ثابت pin شوند، و PR نامطمئن به secretهای production دسترسی نداشته باشد.
- قواعد `main` در GitHub Settings: PR اجباری، تست ضروری، حفاظت در برابر force-push و حذف، بررسی تغییرات حساس توسط مالک، Secret Scanning و Push Protection و Private Vulnerability Reporting در صورت امکان؛ **وجود سند این تنظیمات را خودکار فعال نمی‌کند**.
- branch protection/ruleset را تنها صاحب حساب فعال می‌کند. اگر در API ruleset خالی بود، آن را در گزارش *مانع باز* ثبت کنید؛ ادعا نکنید فعال شده است.

## ۴. آزمون و گیت الزام‌آور

پیش از هر merge:
- TypeScript، تست کل پروژه و build روی **SHA دقیق PR** پاس شوند: `bun run verify` (با دیتابیس مصنوعی ایزوله). در تغییر API و امنیت، تست HTTP منفیِ عدم دسترسی، مرز نقش/دانشجو، دادهٔ خصوصی، خطای ذخیره و پاسخ ۴xx/۵۰۰ اضافه شود.
- `bun run smoke:api` و آزمون محیط staged برای تغییرات runtime/deploy در صورت امکان اجرا و نتیجه صریح ثبت شود. اگر دسترسی نیست «انجام نشده» بنویسید، نه «سبز».
- پس از merge، نتیجهٔ گیت `main` روی SHA ادغامی بررسی شود؛ production فقط با دستور جداگانه، backup/rollback و تأیید اپراتور منتشر شود.
- برای تغییر UI، رفتار موبایل، RTL، کیبورد، dark/light و مسیر onboarding بررسی شود. دستور تغییر ظاهر، نقش یا منوی جدید از مالک گرفته شود؛ قانون معارف بدون توضیح و تأیید او وارد موتور نشود.

## ۵. گزارش و پاسخ به حادثه

1. اطلاعات آسیب‌پذیری، secret و هویت قربانی را **فقط خصوصی** گزارش کنید؛ Issue عمومی فقط توصیف پاک و بدون exploit/دادهٔ حساس داشته باشد. [سیاست گزارش امن](../SECURITY.md) را بخوانید.
2. هنگام احتمال افشای credential: ابتدا در محیط صاحب سرویس **revoke/rotate**، بازنشانی نشست‌ها و بررسی audit؛ سپس اسکن/بازنویسی تاریخچه فقط با برنامهٔ پشتیبان و هماهنگی GitHub Support. حذف از HEAD به‌تنهایی درمان نیست.
3. اقدامات حادثه را با تاریخ، SHA، محدودهٔ بررسی، تأیید تست، میزان اثر، ریسک باقی‌مانده، وظیفهٔ اپراتور و وضعیت «باز/بسته» ثبت کنید؛ هیچ ادعای رفع کامل بدون شواهد مستقل ندهید.
4. برای کتابخانهٔ آسیب‌پذیر از تغییر نسخهٔ آزمایشی، تست یکپارچگی، بازگشت‌پذیری و پاسخ مسئولانه استفاده شود. نصب/آپدیت خودکار سرور مجاز نیست.

## ۶. قرارداد مشارکت‌کننده

هر PR لازم است به این پنج پرسش پاسخ دهد: چه داده‌ای می‌خواند/می‌نویسد؟ چه کسی مجاز است؟ ورودی خراب یا خطای دیسک چه می‌کند؟ چه چیزهایی می‌تواند افشا یا کش شود؟ تست و برنامهٔ بازگشت روی کدام SHA اجرا شده؟ اگر پاسخ معلوم نیست، PR هنوز آمادهٔ merge نیست.

این سند باید در `AGENTS.md`، `CONTRIBUTING.md`، قالب PR و `docs/INDEX.md` پیوند شود. **تغییرات آینده باید امنیت را حفظ یا تقویت کنند**؛ هر استثنا با ارزیابی ریسک و تأیید صریح مالک، ثبت مکتوب و تست قابل بازبینی همراه باشد.


### الحاقیهٔ اجباری ۱ نوامبر ۲۰۲۶: قواعد سخت‌گیرانهٔ جدید

- هیچ Login یا GET /me حق **اعطای خودکار نقش** ندارد؛ تغییر دسترسی فقط از جریان Root با audit و ذخیرهٔ کامل پذیرفته می‌شود.
- Logout برای توکن‌های JWT بدون پایگاه نشست دستگاه‌محور باید ابطال سروری انجام دهد؛ نسخهٔ فعلی با افزایش `sessionVersion` تمام نشست‌های قبلی را می‌بندد، نه صرفاً LocalStorage مرورگر.
- API عمومی چارت فقط نسخه‌های **active** را نمایش می‌دهد؛ دسترسی به draft/archived نیازمند مدیر دارای JWT معتبر و مجوز `curriculum.manage` است.
- هر تغییر هویت مدیر، محدودهٔ دسترسی، نیازسنجی خصوصی، پیامک و گروه درسی همراه با audit باید در صورت شکست `db.save()` rollback شود و خطای داخلی بیرون ندهد.
- در Production اجرای سرور با `JWT_SECRET` کوتاه و رمزهای Root/Recovery ضعیف یا یکسان، شمارهٔ روت غیرمعتبر یا `MOCK_OTP_CODE` ممنوع است؛ با خطای شروع سرویس متوقف می‌شود.
- روی OTP Verify، Password Recovery و دانلود تولید ZIP محدودکنندهٔ مستقل نصب شود؛ rate limit حافظه‌ای جایگزین WAF/Shared Store در چند Worker نیست.
- گزارش کامل و دستورکار قابل انجام توسط مالک: [ممیزی جامع امنیت](SECURITY_COMPREHENSIVE_AUDIT_AND_OWNER_ACTIONS_20261101_FA.md).


### الحاقیهٔ فایل‌های قابل دانلود و گزارش خطای سرور

هیچ endpoint عمومی یا ابزار build حق ZIPکردن کل دایرکتوری افزونه را ندارد. فقط فهرست بررسی‌شدهٔ `extension/public-files.json` مجاز است؛ فایل اضافه، symlink، backup، credential و فایل ساختگیِ محیط نباید به دانلود عمومی برسد. هر export دارای دادهٔ خصوصی Root (از جمله بکاپ و Excel) نیازمند audit ذخیره‌شده **قبل از ارسال** است؛ شکست audit باید دانلود را fail-closed کند. پیام خطای Express و لاگ‌ها حق ثبت متن exception، stack، URL و body یا Secret ندارند. با تست‌های مصنوعیِ مسیر محرمانه این قرارداد را پیوسته بررسی کنید.


### الحاقیه: همگام‌سازی آموزشیار و ذخیرهٔ اتمیک

داده‌های افزونه فقط از مسیر **صف تأیید مدیر** وارد می‌شوند؛ نباید حتی پس از بازپخش یا شکست ذخیره به ارائهٔ رسمی خودکار تبدیل شوند. شناسهٔ Job، شمار و محتوای Chunk، `importBatches` و `importRecords` باید در هر نوبت به شکل یک واحد ذخیره شوند و در خطای دیسک به حالت قبلی بازگردند. هر Job دارای سقف مجموع داده و تعداد Chunk و هر کاربر دارای سقف کار نیمه‌تمام است؛ تغییر سقف‌ها به تست مقاوم در برابر سوءاستفاده نیاز دارد.
