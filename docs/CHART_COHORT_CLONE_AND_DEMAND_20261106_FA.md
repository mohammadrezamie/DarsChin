# تحویل هستهٔ چارت‌های مستقل و نیازسنجی یکپارچه — ۱۵ آبان ۱۴۰۵

## اولویت مالک
«برای هر رشته، مقطع، ورودی چارت جدا تعریف کنم» و نیازسنجی همان محدوده، با ابزارهای واقعی مدیر گروه، نه بخش‌های ظاهری یا اصلاحات کوچک.

## ۱) ایجاد و کپی نسخهٔ چارت
- مسیر جدید `POST /api/curriculum/:id/clone` فقط با مجوز `curriculum.manage`، و ورودی `entryYearId`، `version`، `name`، `copyRules` (اختیاری) کار می‌کند. **مقصد فقط یک ورودی متفاوت از همان دانشگاه/واحد/مقطع/رشته** است؛ برای رشته یا مقطع متفاوت باید چارت جدید با فرم پنج‌مرحله‌ای ساخته شود. با این محدودیت قانون مربوط به رشته دیگر تصادفاً منتقل نمی‌شود.
- نسخهٔ مقصد **فقط پیش‌نویس** است. درس‌ها/انتساب گرایش و نیمسال پیشنهادی با ID جدید کپی می‌شوند؛ روابط پیش‌نیاز/هم‌نیاز، درصورت انتخاب مدیر، ID و `curriculumId` تازه می‌گیرند و `entryYearId` محدودشدهٔ معتبر به ورودی مقصد تبدیل می‌شود.
- پیش از کپی، فعال بودن دانشگاه/واحد/مقطع/رشته/ورودی مقصد، اعتبار درس‌ها و گرایش‌ها، عدم تکرار نسخه، سازگاری قواعد و نبود چرخهٔ پیش‌نیاز بررسی می‌شود. ذخیرهٔ چارت، انتساب‌ها، قوانین و لاگ یک **عمل واحد با بازگشت هنگام خطا** است.
- **سوابق دانشجو، ارائه‌های ترمی، تقاضاها، پاسخ‌های نیازسنجی، مجوزها و قواعد حدسی هرگز کپی نمی‌شوند**. حتی چارت کپی‌شدهٔ فعال هم نیست؛ باید ابتدا مدیر تمام درس‌ها/قوانین را برای ورودی مقصد بررسی و پس از آن از پنل منتشر کند.

## ۲) نیازسنجی برای همین رشته و ورودی
- انتخاب مرحله‌ای `دانشگاه ← واحد ← مقطع ← رشته ← ورودی ← نسخهٔ چارت ← گرایش` جای فهرست خام با اولین چارت پیش‌فرض را می‌گیرد. فقط چارت‌های مجازِ حساب مدیر و وضعیت‌های غیرآرشیو در انتخاب نمایش داده می‌شوند؛ احراز مجوز و حوزه در backend همچنان قطعی است.
- هر فرم نیازسنجی متعلق به **دقیقاً یک `curriculumId` و یک `entryYearId`** است. برای نیازسنجی چند ورودی باید فرم‌های جدا ساخت؛ نتایج با هم ادغام نمی‌شوند.
- فهرست دروس از انتساب‌های **فعال همان چارت و گرایش** با حذف تکرار می‌آید. «انتخاب همه»، «پاک کردن»، جستجوی نام یا کد و تعیین `recommendedMinimumByCourse` مستقل برای هر درس اضافه شده است. سقف انتخاب ۱۰۰ درس مطابق API است.
- فرم تا هنگام بارگذاری معتبر چارت، انتخاب آگاهانه نسخه، نیمسال هدف و دروس درست امکان ذخیره ندارد. خطاهای API به کاربر نمایش داده می‌شوند، نه ادعای موفقیت.

## ۳) خروجی مدیریت بدون اطلاعات شخصی
- `GET /api/demand/surveys/:id/summary.csv` با مجوز scoped `demand.manage` یا Root Owner، تعداد تقاضا، حدنصاب پیشنهادی، باقی‌مانده و تعداد خوداظهاری ترم آخر را برای هر درس صادر می‌کند. **نام و شماره دانشجو ندارد.**
- مقدار نام درس و کد قبل از ورود به CSV در برابر تزریق فرمول و شکست ساختار سطر محافظت می‌شود.
- خروجی شناسایی‌کنندهٔ دانشجویان همچنان فقط با `demand.export` یا احراز معتبر Root Owner در API موجود است؛ دکمه خروجی تجمیعی برای مدیر گروه نیز در UI قرار گرفته است.

## ۴) موارد خارج محدوده و کار ناتمام
- «دانشکده» هنوز در اسکیمای این بخش، موجودیت مستقل ندارد. ایجاد رابطه‌های آن بدون طراحی و مهاجرت صحیح و بررسی ارتباط با همهٔ چارت‌های موجود مجاز نیست.
- موتور ترم‌به‌ترم تا فارغ‌التحصیلی، منبع معتبر رتبه‌بندی استاد، نسخه‌بندی پیشرفته و زمان‌بندی انتشار نیازسنجی‌ها کارهای مستقل باقی می‌مانند.
- **معارف کارشناسی پیوستهٔ رشته‌های غیرپزشکی دانشگاه آزاد:** تا شرح دقیق و تأیید مالک هیچ قاعده جدیدی به‌عنوان مقررات قطعی اعمال نشود.
- در این تغییر هیچ استقرار سرور، تغییر لندینگ، حذف دمو، دسترسی به پروژهٔ تکین یا دست‌کاری دادهٔ واقعی انجام نمی‌شود. صفحات دمو فقط برای بررسی موقت‌اند.

## کنترل کیفیت و پذیرش
۱. کپی یک چارت با چند درس و روابط به ورودی متفاوت و بررسی استقلال تمام IDهای چارت، دروس و قوانین.
۲. جلوگیری از کپی تکراری، گرایش یا قانون نامعتبر، ورودی مقصد نامعتبر و تلاش دانشجو برای کپی؛ بازگشت کامل در خطای ذخیره.
۳. نیازسنجی‌های ورودی ۱۴۰۳ و ۱۴۰۴ یک رشته، به چارت متفاوت اشاره کنند؛ انتخاب مشترک/گرایش، دروس غیرفعال/تکراری و حدنصاب مستقل تست شوند.
۴. گزارش تجمیعی scoped فقط آمار درس داشته باشد؛ بدون اطلاعات دانشجو و با محافظت CSV.
۵. CI شامل TypeScript، Vitest و Build در SHA دقیق PR؛ پس از موفقیت ادغام، تست main. **ظاهر موبایل و عملکرد مرورگر واقعی و نسخه منتشرشده فقط پس از بررسی جداگانه تأیید می‌شوند.**
