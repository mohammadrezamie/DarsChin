# بازسازی تاریخچهٔ عمومی درس‌چین و حفظ بک‌لاگ — ۱ نوامبر ۲۰۲۶

## تصمیم مالک و مرزبندی

مخزن اصلی `mohammadrezamie/DarsChin` باید Public و MIT باقی بماند. با توجه به افشای دیتابیس قدیمی و اسکریپت‌های حاوی رمز، مالک اعلام کرده استقرار آتی را از ابتدا با دیتابیس و رمزهای **کاملاً تازه** انجام می‌دهد. هیچ اقدامی روی سرور فعلی/اتصال کنونی آن انجام نشده و نباید برنامهٔ جدید با `git pull` روی Checkout قدیمی مستقر شود. پس از پاک‌سازی تاریخچه، باید روی سرور **clone تازه** با بکاپ/مهاجرت مورد تأیید اپراتور انجام شود.

## برنامهٔ نجات تاریخچهٔ Git

در نسخهٔ اصلی، اسکریپت‌های محرمانه و فایل دیتابیس از HEAD حذف شده‌اند؛ ولی تاریخچهٔ قدیمی این فایل‌ها را نگه می‌داشت. نخستین Commit مخزن تنها README داشت و بدون فایل دیتابیس/اسکریپت بود؛ بنابراین از آن به‌عنوان والدِ ایمنِ Snapshot جدید سورس استفاده شد. هر شاخهٔ قدیمی باید به Snapshot مستقل با والدِ پاک و بدون فایل `data/darschyn-db.json` یا ابزار اجرایی `scripts/legacy/` منتقل شود. این اقدام تاریخچهٔ توسعهٔ قبلی و SHAهای آن را **قطع می‌کند** و رفتار Pull در Cloneهای قدیمی تغییر می‌کند؛ داکیومنت‌ها و کد نسخهٔ اصلی در Tree جدید حفظ می‌شوند.

**بسیار مهم:** بازنویسی شاخه‌ها به‌تنهایی اطلاعات را از `refs/pull/*`، کش‌های GitHub، Forkها و Cloneهای قدیمی پاک نمی‌کند. بعد از اتمامِ بازنویسی شاخه‌ها و بازبینی refها، حذف کش/ارجاعات PR توسط GitHub Support طبق [دستورالعمل رسمی GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) لازم است؛ امکان انجام آن از طریق مجوز محدود اتصال ChatGPT وجود ندارد. هیچ ادعایی دربارهٔ باطل‌شدن رمز/نشست قدیمی بدون اجرای واقعی چرخش اعتبارنامه روی سرویس زنده وجود ندارد.

## مراحل باقی‌ماندهٔ حادثه

1. بررسی همهٔ Branchهای مستقل و Tags برای نبود ancestry آلوده. PRهای قدیمی به دلیل ارجاعات داخلی GitHub ممکن است همچنان Source قدیمی را نشان دهند.
2. هماهنگی با GitHub Support برای حذف PR refs/cache پس از بازنویسی لازم؛ Forkها و Cloneهای دیگر قابل حذف از سوی ما نیستند.
3. همهٔ رمزهای/کلیدهای احتمالی افشاشده (از جمله Root، نشست‌ها و حساب‌های تاریخی) در نصب‌های زنده باید باطل یا تعویض شوند. نصب تازه صرفاً از ENV خصوصی جدید و DB نو استفاده کند.
4. تنظیم محافظت شاخهٔ `main` پس از پاک‌سازی با Check الزامی. سطح مدیریت GitHub از طریق اتصال حاضر در دسترس نیست.
5. پس از اتمام حادثه، توسعهٔ محصول طبق اولویت و تست واقعی موبایل پیگیری شود.

این سند نه حاوی رمز است و نه دادهٔ شخصی، و نباید هیچ نمونهٔ قدیمی را به ریپو برگرداند.
