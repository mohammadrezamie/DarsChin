# طرح بازطراحی اساسی درس‌چین: تجربهٔ دانشجو، مدیریت مستقل، گراف آموزشی و راهنما

**تاریخ:** ۲۰۲۶/۱۰/۲۸ (۱۴۰۵/۰۸/۰۶)  
**وضعیت:** تصمیمات مالک ثبت و بخشی از «جداسازی عمومی / راهنمای دانشجو / هستهٔ تحلیل گراف / تک‌ریشه‌ای‌بودن مدیریت» روی PR این سند پیاده شده است. **پنل مدیریت جدید، ادیتور گرافیکی و خروجی Excel هنوز آماده نیستند.**

## ۱. تفکیک مطلق مخاطب محصول

- **بازدیدکننده/دانشجو:** صفحهٔ عمومی تنها روی فایدهٔ انتخاب واحد تمرکز کند: درس‌های ارائه‌شده، پیش‌نیازها، جدول هفتگی، صف سریع ثبت، پیشنهاد و نیازسنجی. هیچ معرفی/لینک/راهنمای عمومی برای ابزار داخلی ادمین وجود نداشته باشد.
- **ادمین:** تنها بعد از احراز هویت واقعی و مجوز سمت سرور، در ناوبری حساب یک ورودی مستقل به «مدیریت» پیدا می‌کند؛ همراه با میز کار دانشجوییِ خودش. اطلاعات/endpointهای مدیر هرگز به صرف مخفی‌کردن دکمه امن نمی‌شوند: هر درخواست نیازمند احراز مجوز و scope واقعی است.
- **ریشهٔ واحد:** فقط رکورد رزروشدهٔ `usr-super` از بوت‌استرپ محیط حق `super-admin` دارد؛ روت نمی‌تواند از API مدیریت نقش، روت دیگری بسازد یا خودش را تنزل دهد. سطح admin و scopeهای میانی قابل واگذاری‌اند.
- **دموی مدیر:** محیط QA فقط به اکانت دارای دسترسی مدیریتی قابل نمایش باشد، نه به بازدیدکنندهٔ عمومی. مسیرهای Synthetic واقعیِ کاربر نیستند و در SEO ایندکس نمی‌شوند.

## ۲. موبایل تقریباً مثل اپلیکیشن، دسکتاپ با فضای کار حرفه‌ای

- موبایل دانشجو: نوار پایین با ۳–۵ مقصد مهم، «بیشتر» برای باقی، Safe Area آیفون، کنترل‌های ۴۴px به بالا، اسکرول داخلی محدود، Header کوتاه و وضعیت ذخیرهٔ واضح. گردش‌ها باید thumb-friendly باشند؛ لیست، کارت فشرده، Bottom Sheet، جست‌وجو و بازخورد لمس.
- موبایل مدیر: **فضای مجزا**، نه کپی نسخهٔ دسکتاپ داخل WebView. Navigation drawer، سربرگ چسبان عنوان بخش، اقدام اصلی در دسترس و فیلتر/ویرایش در چند مرحلهٔ کوتاه.
- دسکتاپ/تبلت: صفحهٔ سایدبار + محتوای اصلی + inspector جزئیات، انتخاب چند آیتم، keyboard shortcuts و فضاهای گستردهٔ گرافیکی. در نمایشگر عریض، محتوا با max width و density کنترل‌شده باقی بماند؛ تلویزیون جایگزین جدول بی‌نهایت شلوغ نشود.
- PWA: فقط بعد از طراحی manifest آیکون‌ها، سیاست به‌روزرسانی و cache، نصب اختیاری `Add to Home Screen` اضافه شود. **هیچ پاسخ API خصوصی، PII، SMS یا توکن نباید در Cache عمومی سرویس‌ورکر ذخیره شود**. آفلاین فقط برای shell/راهنما و پیش‌نویس غیراحساس با رفتار همگام‌سازی روشن قابل پذیرش است.
- دسترس‌پذیری: WCAG 2.2 AA، `prefers-reduced-motion`، فوکوس و صفحه‌خوان RTL، ورودی متنی جایگزین Drag&Drop. قابلیت واقعی را فدای 3D تزئینی نکنیم.

## ۳. مرکز راهنمای دو سطحی

- راهنمای کلی داخل میز کار دانشجو: همهٔ ۷ قسمت در یک فهرست، مسیر پیشنهادی، لینک مستقیم و FAQ مستقل. از داده/قانون ساختگی به‌عنوان دستور رسمی دانشگاه استفاده نشود.
- هر بخش: یک `details` کوتاه «این بخش چه کاری می‌کند؟»، سه قدم کاربردی و یک هشدار مرتبط. موبایل در حالت بسته فضای زیادی نگیرد.
- راهنمای مدیر کاملاً جداست: بسته به permission فقط اقدام‌های مجاز هر مدیر (ایجاد کاتالوگ، چارت، واردکردن، بررسی، کاربران و نیازسنجی) نشان داده شود؛ برای مدیر گروه، راهنمای مدیریتی PII فقط در محدودهٔ مجاز.
- گام بعد: walkthrough مرحله‌ایِ اختیاری برای کاربر تازه‌وارد، دکمهٔ ردکردن، بازکردن دوبارهٔ آموزش، وضعیت نسخهٔ راهنما. پیاده‌سازی با دادهٔ مصنوعی و تست واقعی مرورگر.

## ۴. بازسازی پنل مدیر، بدون سؤال از «کد استان»

### ساختار پیشنهادی ناوبری (اول UX، سپس API)

1. **پیشخوان:** وضعیت سلامت داده‌ها، فعالیت‌های اخیر، کارهای نیازمند تأیید، هشدارها، و میانبر اکشن‌های رایج؛ کارت‌های قابل تنظیم با قابلیت واقعی.
2. **ساختار آموزشی:** انتخاب سلسله‌مراتبی «دانشگاه ← واحد ← مقطع ← رشته ← گرایش اختیاری ← ورودی» با نام قابل جست‌وجو، breadcrumb و comboهای وابسته. شناسه‌ها فقط در دادهٔ API پنهان‌اند.
3. **کاتالوگ و چارت:** افزودن گروهی درس، ویرایش چارت، نسخه‌بندی/پیش‌نویس/بازبینی، import از آموزشیار با پیش‌نمایش diff و تأیید انسان. قانونی که تأیید نشده نباید به همهٔ ورودی‌ها تعمیم یابد.
4. **نقشهٔ روابط:** گره درس + یال جهت‌دار پیش‌نیاز (فلش توپر) + یال هم‌نیاز (خط‌چین بدون ترتیب) + گروه‌های منطقی AND/OR؛ Edge validator با خطا قبل از ذخیره، History/Undo/Redo، Zoom/Fit, auto-layout، search، panel جزئیات و ورود متنی جایگزین. کاربر یک لبهٔ تازه با اتصال دو node بسازد؛ backend آن را به `AcademicRule.expression` معتبر تبدیل کند و از دور/رشته‌نامعتبر جلوگیری کند.
5. **ارائه‌ها و نیمسال:** گروه‌ها، ظرفیت/زمان/استاد، تاریخ امتحان، فیلتر، واردکردن فایل و مغایرت‌ها؛ روابط به چارت و درس‌های وابسته با لینک‌های واضح.
6. **نیازسنجی:** فقط حوزهٔ مجاز و ورودی، خلاصه + پاسخ دانشجو با مجوز جدا؛ دادهٔ دانشجو برای نقش مدیریتی خارج از scope هرگز ارسال نشود.
7. **مرکز کاربران:** یک فهرست با نام، موبایل، شمارهٔ دانشجوییِ ثبت‌شده، واحد/رشته/ورودی، وضعیت تأیید و نقش؛ جست‌وجو و فیلتر role/scope. تغییر role فقط توسط مجاز سمت سرور و به همراه audit.
8. **پیامک و خروجی:** خروجی `.xlsx` واقعی از زیرمجموعهٔ فیلترشدهٔ مجاز، جدا از سیستم نقش/مدیریت؛ تاریخ/مقصد/فیلتر/علت صادرات ثبت شود. پیش‌نمایش تعداد مخاطب و حذف duplicate؛ رمز/توکن/پروفایل حساس هرگز در خروجی نباشند. اکسل باید جلوی Formula Injection را بگیرد. ارسال پیامک تنها به مخاطبِ دارای رضایت و مبنای اطلاع‌رسانی مجاز، با opt-out، rate limit، audit، صف و قابلیت cancel؛ شماره تلفن دیتابیس به معنی رضایت تبلیغاتی نیست.
9. **لاگ و تنظیمات:** مدیریت خطا، سلامت نیازسنجی، نقش‌ها و برچسب‌های انسان‌خوان؛ Root-only برای بخش‌های حساس.

### سیاست نقش‌ها

`student`: فقط میز کار خود؛ `admin`: صرفاً پنل و قابلیت‌های تخصیص‌یافته؛ `demand manager`: فقط گزارش محدودهٔ تعریف‌شده؛ `super-admin`: فقط Root واحد، ایجاد/ویرایش سایر ادمین‌ها و دریافت گزارش‌های مجاز. مجوز frontend تنها «نمایش» است؛ authorize سمت سرور و object scope شرط لازم هر API است. هر عملیات حساس، قبل از mutate شدن داده‌ها بررسی شود.

## ۵. الگوریتم ارزش زنجیره‌ای درس‌ها؛ نه صرفاً وابستگی ترم بعد

- گراف `G=(V,E)` برای **هر چارت معتبر**، یال `prerequisite -> dependent`. corequisite یال جدا بدون جهت اولویت زمانی. `AND/OR` به معنی احتمال/جایگزینی است، نه تضمین رفع مانع؛ شرط‌های ترم‌آخر و حداقل واحد مستقل‌اند.
- `directUnlocks` تعداد درس‌های مستقیم بعدی؛ `downstreamUnlocks` تعداد **درس‌های یکتای قابل رسیدن در همهٔ ترم‌های آینده**؛ `longestChain` عمق بلندترین زنجیره. شمارش مسیرهای موازی باید unique باشد؛ نه جمع‌زدن تکراری.
- مثال فرضی: A فقط پیش‌نیاز B است، اما B پیش‌نیاز C,D,E,F است. پس اثر احتمالی A برابر ۵ درس پایین‌دست و اثر B چهار درس است. این شاخص کمک به **اولویت‌بندی قابل توضیح** است، نه حکم قطعی انتخاب واحد.
- گراف دارای cycle نامعتبر، rule خارج از چارت یا مبهم باید گزارش و قبل از نمایش رتبه از نظر مدیر بررسی شود. `OR` در نتایج برچسب «ممکن، نه قطعی» دریافت می‌کند. اطلاعات معتبر/پاس‌شدهٔ خود دانشجو، واحد و زمان ارائه بعداً در امتیاز شخصی‌سازی می‌شوند.
- فاز ۱ هستهٔ محاسبات با تست و دادهٔ مصنوعی؛ فاز ۲ نمای دوبعدی React Flow و ELK/Dagre؛ فاز ۳ پس از عملکرد و دسترس‌پذیری، گزینهٔ **سه‌بعدی فقط برای مرور و نمایش**، نه پیش‌فرض ویرایش؛ نسخهٔ دو بعدی/لیستی همیشه باید در دسترس بماند.

## ۶. تحقیقات فناوری و UX

- `@xyflow/react` برای node/edge/handles و تعامل keyboard و a11y مستند است: https://reactflow.dev/learn/customization/handles و https://reactflow.dev/learn/advanced-use/accessibility
- برای DAG chart: `Dagre` چیدمان ساده و `ELK` برای شبکهٔ بزرگ‌تر و محدودیت‌های پیچیده‌تر، با مقایسهٔ رسمی: https://reactflow.dev/learn/layouting/layouting . قبل از نصب، اندازهٔ bundle و نگه‌داری بررسی شود.
- مجوز و اطلاعات PII باید object-scoped و least-privilege باشد (OWASP): https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html
- الگوریتم رسیدن به همهٔ نوادگان و longest chain باید جدا از Render/UI تست شود؛ کنترل cycle را سمت سرور هم باید اعمال کرد.
- فاز بعدی طراحی UX باید Wireframe موبایل/دسکتاپ، رسیدگی به حالت خالی/خطا، چند اقدام واقعی پرمصرف و تست با ۳–۵ سناریوی دانشجویی/ادمین داشته باشد؛ زیبایی «صرف» معیار پذیرش نیست.

## ۷. یادآوری الزام مهم چارت معارف

**در گفت‌وگوی بعدی دربارهٔ چارت معارف دانشگاه آزاد از مالک بپرسیم.** کاربر گفته محتوای دروس معارفِ کارشناسی پیوستهٔ غیرپزشکی از نظر او ثابت است و می‌خواهد جزئیات را بعداً توضیح دهد. تا زمانی که **فهرست دقیق درس‌ها، واحدها، ارتباط‌ها، ورودی‌های مشمول، استثناها و منبع معتبر** از مالک/سند مصوب تأیید نشده، هیچ چارتِ ثابت یا قانون خودکار ساخته نمی‌شود. این مورد در بک‌لاگ `P0 academic rules intake` باز می‌ماند.
