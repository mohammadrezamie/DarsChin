# P0 — بازگردانی امن فهرست آموزشی و حفاظت از اطلاعات زندهٔ دانشجو

**تاریخ:** ۱۴۰۵/۰۸/۰۶ (۲۸ اکتبر ۲۰۲۶)  
**محدودهٔ تغییر:** فقط `mohammadrezamie/DarsChin` و محیط آزمایشی ایزوله؛ نه سرور تولید، نه ریپوی تکین و نه سایر مخازن.

## مشکل بحرانی کشف‌شده

مسیر مدیر `POST /api/admin/restore` قبل از احراز موفقیت ذخیره‌سازی فایل، `db.data` در حافظه را با دادهٔ بارگذاری‌شده عوض می‌کرد. اگر عملیات `rename` یا دیسک شکست می‌خورد، فایل قدیمی پابرجا ولی دادهٔ در حال سرویس جدید می‌شد. ذخیرهٔ بعدی یک درخواست دیگر می‌توانست تغییرات ثبت‌شدهٔ دانشجو را بی‌سروصدا بازنویسی کند.

همچنین شکل قبلی Restore کل فهرست‌های دانشجویی را از بکاپ قدیمی جایگزین می‌کرد، با اینکه `users` فعلی را حفظ می‌کرد؛ در نتیجه امکان ازبین‌رفتن برنامهٔ انتخاب واحد، تاریخچهٔ نیازسنجی و ایجاد دادهٔ ناسازگار با کاربران وجود داشت. خروجی بکاپ مدیریت هم امکان داشت تنظیمات محرمانهٔ ارائه‌دهندهٔ پیامک را همراه اطلاعات دیگر صادر کند.

## قرارداد جدیدِ مسیر تحت وب

- مسیر Restore **فقط فهرست آموزشی** (دانشگاه/واحد/رشته/ورودی/چارت/دروس/قوانین و گروه‌ها) را از یک Snapshot کامل و معتبر بازگردانی می‌کند؛ **بازگردانی کامل کاربران و پاسخ‌های شخصی از بکاپ از طریق مرورگر عمداً مجاز نیست**.
- حساب‌ها، رمزها و نسخهٔ نشست JWT، برنامه‌ها و دروس گذراندهٔ دانشجو، نیازسنجی‌ها و پاسخ‌ها، تاریخچهٔ پشتیبانی و ممیزی، OTP/CAPTCHA، تنظیمات و تاریخچهٔ SMS، تنظیمات آموزشی جاری، و وضعیت sync/import فعلی **حفظ می‌شوند**.
- مجموعه‌های لازم باید واقعاً وجود داشته باشند، از نوع آرایه باشند و شناسهٔ منحصربه‌فرد و معتبر داشته باشند؛ دادهٔ ناقص/ناسازگار HTTP 400 می‌گیرد.
- قبل از نوشتن، ارجاع درس‌های چارت، گروه‌ها، برنامه‌های فعلی دانشجو، دروس گذرانده و نیازسنجی‌ها با کاتالوگ جدید کنترل می‌شود؛ Snapshot ناسازگار بدون دست‌زدن به حافظه یا فایل **رد می‌شود**.
- Snapshot ابتدا در یک candidate مستقل ساخته می‌شود. `writeDurableJson` فایل موقت `0600` را fsync و rename می‌کند، و فقط **پس از rename موفق** دادهٔ داخل حافظه را جابه‌جا می‌کند. اگر بعد از rename، flush پوشه شکست بخورد، دادهٔ زنده همچنان با فایل قابل‌مشاهده هماهنگ می‌ماند ولی API خطا اعلام می‌کند و اپراتور باید وضعیت دیسک را بررسی کند.
- خروجی قابل دانلودِ مدیر دیگر کلید/تنظیمات سرویس پیامک و تاریخچهٔ ارسال SMS را صادر نمی‌کند. با این حال **سایر داده‌های هویتی/پشتیبانی و پاسخ‌های دانشجو در بکاپ وجود دارند و بکاپ کاملاً محرمانه است**؛ آن را در کانال عمومی یا ریپو نگذارید.
- API پیام موفقیت جدید صریحاً اعلام می‌کند **فقط فهرست آموزشی** بازگردانی شده و اطلاعات جاری دانشجویان دست‌نخورده‌اند.

## بازیابی فاجعه‌ایِ کامل، مسیر دیگری است

برای بازگرداندن حساب/برنامه/نیازسنجی پس از ازدست‌رفتن دیسک، یک عملیات **آفلاین** با توقف تمام writeها، نسخهٔ پشتیبان رمزگذاری‌شده و SHA بررسی‌شده، بررسی کامل schema و سازگاری نسخهٔ برنامه و تست restore در محیط ایزوله لازم است. endpoint وب مدیر **به‌هیچ‌وجه جایگزین Disaster Recovery نیست**.

## پوشش آزمون و محدودیت‌ها

`tests/catalog-restore-safety.test.ts` شامل رد ورودی ناقص، شناسهٔ تکراری، حفظ اطلاعات شخصی/کلید محرمانه، رد قطع ارتباط دروس با برنامهٔ فعلی، و شبیه‌سازی خرابی rename و fsync است. همهٔ تست‌ها با دادهٔ کاملاً ساختگی در پوشهٔ موقت اجرا شوند. `bun run qa:full` و مرور کامل تعامل مدیر جداگانه اجرا و نتیجهٔ واقعی همراه SHA در PR ثبت شود.

**محدودیت مهم:** دادهٔ JSON یک‌فرایندی هنوز پایگاه‌دادهٔ مناسب concurrency سنگین/چند instance نیست. حتی با این اصلاح، باید پیش از ورود انبوه دانشجویان، پایگاه‌دادهٔ تراکنشی، بکاپ رمزگذاری‌شده و آزمون بازیابی واقعی طراحی شود.

## اصلاح یکپارچگی دادهٔ نمونه و گیت واقعی — ۱۴۰۵/۰۸/۰۶

حین اجرای گیت جامع، آزمون API تولیدی روی Snapshot خودِ برنامه به‌درستی شکست خورد: seed قدیمی `universities: []` داشت ولی واحدها و چارت‌ها به `univ-azad` ارجاع داده بودند؛ قانون `pr-18` نیز به درس `crs-power-lab` غایب اشاره می‌کرد. **به‌جای تضعیف اعتبارسنجی**، فقط دادهٔ ساختگی/دمو اصلاح شد: رکورد عمومی دانشگاه اضافه شد و قانون ارجاع‌دهنده به درس ناموجود حذف شد. از این رکورد نباید قانون رسمی دانشگاه استنباط شود؛ دیتابیس‌های موجود خودکار تغییر نمی‌کنند و برای اصلاح کاتالوگ قدیمی باید پشتیبان‌گیری و راهکار اپراتوری بررسی‌شده انجام شود.

**آزمون واقعی نهایی روی نسخهٔ یکپارچه:** `bun run qa:full` با نصب قفل‌شدهٔ Bun، TypeScript، **۳۳۵ تست موفق در ۶۲ فایل**، بسته‌بندی افزونه، بیلد Vite و Express، و API smoke تولیدی با دادهٔ موقت، شامل HTTP 400 برای بکاپ معیوب و HTTP 200 برای بازگردانی صرفاً کاتالوگ، همگی **exit 0**. دو تست اضافی صحت ارتباطات دادهٔ نمونه را کنترل می‌کنند. اجرای این گیت دلیل سالم‌بودن VPS، Safari واقعی یا بازگردانی واقعی از نسخهٔ پشتیبان نیست.
