# ممیزی امنیتی گسترده و دستورکار عملی مالک — ۱ نوامبر ۲۰۲۶

> **مهم:** این گزارش جایگزین تست نفوذ مستقل نیست و به‌معنای امن‌بودن کامل نیست. وضعیت «اصلاح کد» فقط پس از CI سبز روی SHA دقیق و ادغام ثبت می‌شود. بررسی Credentialهای واقعی و حذف نسخه‌های حساس از تاریخچهٔ قدیمی GitHub بدون اقدام مالک و GitHub Support انجام‌شدنی نیست. هیچ مقدار محرمانه‌ای را در GitHub عمومی وارد نکنید.

**تغییر دامنهٔ محصول:** Logout جدید برای امنیت، همهٔ دستگاه‌های کاربر را خارج می‌کند؛ تا زمان پیاده‌سازی Session Store دستگاه‌محور این مصالحه آگاهانه است. در نسخهٔ پیشین Logout سرور توکن را باطل نمی‌کرد.

### مواردی که در کد قبلاً رفع شده و دوباره بررسی شدند

- حذف دیتابیس runtime و اسکریپت‌های منسوخ از tree فعلی و گیت `repo:public-check`، حفاظت از فایل اجرایی server.cjs و sourcemap در سرویس استاتیک، تست ضدّ account enumeration در login و OTP؛
- احراز هویت و مالکیت رکوردهای دانشجو، Root مخصوص شناسهٔ رزرو شده، عدم اعتماد به نقش‌های JWT و frontend، OTP یک‌بارمصرف و revoke توکن بعد از تغییر رمز؛
- ذخیرهٔ اتمیک JSON برای یک فرآیند، rollback بخش پشتیبانی/ثبت‌نام/سوابق درس؛
- تست‌های مصنوعی/ایزوله و سیاست دائمی [امنیت مشارکت‌کنندگان](PERMANENT_SECURITY_POLICY_FA.md).

**توجه:** بررسی فایل‌های کد و سبزشدن تست، به معنای اثبات نبود هر آسیب‌پذیری دیگر نیست. بخش‌هایی مثل واردسازی، مهاجرت دیتابیس، هم‌زمانی چندپردازشی، امنیت reverse proxy، افزونهٔ مرورگر و وابستگی‌ها باید مستقل در تست نفوذ و audit بعدی بررسی شوند.

## اقدام‌های مالک در GitHub — بدون نیاز به دستکاری VPS فعلی

### P0-A — پاک‌سازی تاریخچهٔ افشاشده (فقط با هماهنگی GitHub Support)

1. وارد https://support.github.com/ شوید، با حساب مالک GitHub درخواست «**Remove sensitive data from repository history / cached PR views**» برای `mohammadrezamie/DarsChin` ثبت کنید.
2. توضیح دهید repository قبلاً Private بوده و سپس Public شده و در تاریخچهٔ قدیم احتمال وجود دادهٔ runtime و اسکریپت‌های دارای رمز بوده است؛ `main` بازسازی شده، اما metadata/commits بعضی PRهای بسته هنوز قابل دسترسی‌اند. شناسه‌های قدیمی قابل پیگیری: #27، #28، #29، #37، #42، #56، #71. **خود رمزها، فایل حساس، هش‌ها یا نمونهٔ دیتابیس را در تیکت عمومی/Issue نگذارید.**
3. از پشتیبانی بپرسید کدام `refs/pull/*`، cached diffها و فایل‌های قابل‌دانلود تحت پروسهٔ پاک‌سازی قرار می‌گیرند، آیا first changed commit / `git-filter-repo` لازم است و چه پیامدهایی برای PRها دارد.
4. حذف از HEAD، Merge Squash و پاک‌کردن branch به‌تنهایی refهای قبلی، cloneها و forkهای دیگران را حذف نمی‌کند؛ اسناد GitHub را بخوانید:
   https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository
5. **هیچ Force Push/Rebase روی main فعلی یا اتصال سرور موجود بدون برنامهٔ هماهنگ بکاپ و تأیید مالک انجام نشود.**

### P0-B — تعویض اطلاعات اعتباریِ احتمالاً افشاشده در محیط واقعی

1. **فقط در محیط محرمانهٔ خودت** فهرست Secrets قدیمی را از نسخه‌های مصرف‌شده تهیه کن؛ هر چیزی که واقعاً در Git بوده و هنوز معتبر است افشاشده فرض شود (رمز Root، Recovery، JWT، API پیامک، CAPTCHA، token دسترسی/استقرار، deploy keys). مقدار هیچ‌کدام را در چت یا Issue عمومی منتشر نکن.
2. برای هر سرویس، کلید را از **پنل رسمی ارائه‌دهنده** باطل و کلید تازه بساز؛ دربارهٔ JWT، تعویض `JWT_SECRET` همهٔ نشست‌های امضاشدهٔ قبلی را باطل می‌کند. اگر رمز مشترک استفاده شده، آن را در سرویس‌های دیگر هم تغییر بده.
3. دیتابیس، اطلاعات دانشجو و Backup را به‌طور خودکار حذف نکن؛ قبل از نصب تازه یک بکاپ رمزنگاری‌شده و تست بازگردانی لازم است. طبق تصمیم مالک، اتصال قدیمی VPS به Repo دست‌نخورده می‌ماند تا استقرار تازه جداگانه طراحی شود.
4. اگر از حساب واقعی دانشجویان در فایل‌های قدیمی نمونه‌ای بیرون رفته، ارزیابی رویداد نقض داده و تکالیف اطلاع‌رسانی/حقوقی را متناسب با مقررات محل اجرا انجام بده.

### P0-C — تنظیمات محافظت GitHub (حساب مالک)

1. روی موبایل یا دسکتاپ به `github.com/mohammadrezamie/DarsChin` → **Settings** → **Rules** → **Rulesets** برو. یک **New branch ruleset** فعال با target `main` بساز: **Require a pull request before merging**، **Require status checks to pass** (چک `Typecheck / Tests / Build`)، Block force pushes، Restrict deletions. برای پروژهٔ تک‌نگه‌دارنده approvals اجباری را بر اساس سیاست review خودت تعیین کن تا merge قفل نشود.
2. از **Settings → Advanced Security**، Secret Scanning، Push Protection و **Private vulnerability reporting** را در صورت وجود برای مخزن فعال کن. از بخش Security یا Settings، Dependabot alerts و security updates را بررسی کن. پشتیبانی این گزینه‌ها بسته به حساب/مخزن متفاوت است؛ بدون دیدن صفحه، روشن‌بودن را ادعا نمی‌کنیم.
3. یک PR آزمایشی غیرحساس باز کن و بررسی کن Push مستقیم روی `main` و Merge بدون چک سبز واقعاً مسدود است. اگر نیازمند review codeowners هستی، قوانین CODEOWNERS را با توجه به تک‌نگه‌دارنده بودن تنظیم کن.
4. وضعیت فعلی اتصال: `GET /rulesets` **هیچ ruleset نشان نداد**، اما `GET /branches/main/protection` پاسخ **403 Resource not accessible by integration** داشت؛ دربارهٔ سایر انواع branch protection نمی‌توانیم ادعای قطعی کنیم.

### P0-D — قبل از نصب VPS تازه

- محیط تازه را با `NODE_ENV=production`، JWT/Root/Recovery مستقل و قوی، SMS واقعی تأییدشده، HTTPS/TLS، محدودیت IP/Rate Limit/WAF، proxy مورداعتماد، DB خارج Git، backups و rollback تنظیم کن.
- `DARSCHYN_REQUIRE_EXISTING_DB=true` را **فقط بعد از اولین استقرار و تست پشتیبان** فعال کن تا گم‌شدن mount موجب آغاز دیتابیس نمونه نشود.
- JSON DB فعلی برای چند replica/worker مناسب نیست؛ قبل از مقیاس‌پذیری به دیتابیس تراکنشی اشتراکی و rate limiter مشترک مهاجرت کن.
- بعد از استقرار، `bun run verify`، `bun run smoke:api`، بررسی restart/persistence/restore، تست موبایل واقعی، API بدون توکن، localhost/proxy، و تست احراز هویت/OTP را جداگانه انجام بده. فقط موفقیت Vercel frontend نشان‌دهندهٔ سلامت backend نیست.
- تا وقتی این موارد انجام نشده‌اند، محیط را برای دادهٔ واقعیِ عمومی آماده اعلام نکن.

## گیت و مدارک پذیرش

موفقیت CI روی PR و `main`، اجرای مستقل تست‌های خطای ذخیره‌سازی و محدودکننده‌ها و رسیدگی به موارد P0-A/B/C باید **سه مدرک جدا** داشته باشند. مسئلهٔ عمومی [#4](https://github.com/mohammadrezamie/DarsChin/issues/4) را تا تأیید مالک و پشتیبانی باز نگه دارید. متن اطلاعات حساس را به آن منتقل نکنید.
