# استاندارد دائمی فارسی‌نویسی و هویت ایرانی درس‌چین

**تاریخ تصویب: ۱ نوامبر ۲۰۲۶ | دستور صریح مالک | لازم‌الاجرا برای همهٔ مشارکت‌کنندگان، دستیارها، عامل‌های خودکار و PRهای آینده**

## اصل تصمیم

**درس‌چین پروژه‌ای ایرانی است؛ زبان اصلی و ماندگار مستندات رسمی GitHub آن فارسی معیار، روان و راست‌به‌چپ است.** از این پس مستندات جدید، توضیح‌های جدید فایل‌های موجود، متن الگوی PR، راهنمای نصب، سیاست امنیتی، راهنمای مشارکت، گزارش توسعه، مستند محصول و مستندات تجربهٔ کاربری نباید به انگلیسی نوشته شوند.

این تصمیم شامل مستندات پوشه‌های ریشه، `docs/`، `deploy/`، `extension/`، `.github/` و راهنمای ابزارهای داخل `scripts/` است؛ **صرف وجود پسوند `_FA` برای فارسی‌بودن کافی نیست**. هر بار که سندی ویرایش می‌شود، متنِ قابل‌خواندنِ همان بخش باید فارسی و هماهنگ با باقی اسناد شود.

## مواردی که باید دقیقاً حفظ شوند

- **کد برنامه و قراردادهای فنی:** نام توابع، متغیرها، API routeها، schemaها، نام فایل‌ها، دستورات خط فرمان، نشانی URL، Environment Variable، فرمت دادهٔ ورودی، خروجی آزمون و شناسه‌های GitHub به‌خاطر ترجمه تغییر نکنند. در متن فارسی داخل backtick بیایند.
- **مجوز حقوقی `LICENSE`:** متن اصلی مجوز MIT برای اعتبار حقوقی به زبان اصلی باقی بماند؛ می‌توان راهنمای فارسی توضیحی خارج از فایل مجوز افزود اما متن مجوز را بازنویسی نکرد.
- **نقل‌قول تاریخی/خروجی ماشین/اسناد بیرونی:** متن اصلی در صورت نیاز به استناد، داخل بلوک نقل‌قول یا کد حفظ شود؛ در همان سند شرح فارسی قابل‌فهم داشته باشد. لازم نیست URI و نام برند/کتابخانه به فارسی بازنویسی شوند.
- **نام فایل‌های مستندات موجود:** برای جلوگیری از شکست لینک‌ها لزوماً تغییر نمی‌کنند؛ نام انگلیسی مسیر با محتوای فارسی مغایرتی ندارد. فایل جدید باید نام فنیِ قابل فهم و در صورت مناسب پسوند `_FA` داشته باشد.
- **رابط چندزبانهٔ محصول:** اصل فارسی‌محوری به معنی حذف پشتیبانی زبان انگلیسیِ مورد تأیید نیست. فارسی و RTL پیش‌فرض تجربهٔ ایرانی هستند؛ در زبان انگلیسی چیدمان LTR و منوی مربوطه مطابق تنظیمات اجرا شود.
- **مقررات آموزشی ایران:** بدون منابع رسمی، توضیح جزئیات و تأیید مالک، هیچ قانون قطعی دربارهٔ معارف دانشگاه آزاد کارشناسی پیوستهٔ غیرپزشکی ساخته نشود. فارسی‌کردن سند هیچ مجوزی برای تغییر نتیجهٔ موتور آموزشی نیست.

## اصول نگارش

1. از فارسی معیار طبیعی و اصطلاحات روشن استفاده کنید. برای اصطلاح تخصصی در اولین کاربرد، معادل فارسی و در صورت نیاز نام رایج انگلیسی را داخل پرانتز بیاورید؛ در ادامه معادل فارسی کافی است.
2. ترتیب‌های زمانی، تاریخ تصمیم و نسبت منسوخ/فعال بودن را دقیق نگه دارید؛ اسناد قدیمی را با ادعای امروز بازنویسی نکنید. اگر سند به زمان گذشته مربوط است، «گزارش تاریخی ــ تاریخ ...» درج کنید.
3. سرفصل‌ها، جدول‌ها، لینک‌های داخلی، هشدارهای امنیتی، چک‌لیست پذیرش، مراحل و نمونه دستورها حفظ شوند؛ ترجمه نباید متن فنی را خلاصهٔ گمراه‌کننده کند.
4. فایل‌ها و توضیح درخواست ادغام باید محدودیت، آزمون اجراشده، نسخهٔ دقیق، تغییر روی `main` و کارهای انجام‌نشده را به فارسی صریح بیان کنند؛ از ادعای تأیید اجرای تست یا استقرار بدون شاهد پرهیز کنید.
5. در فارسی‌نویسی، فاصله/نیم‌فاصله، نشانه‌گذاری، اعداد، جهت راست‌به‌چپ و نمایش مسیرهای لاتین را کنترل کنید؛ نمایش قطعه‌کد و commandها LTR و دست‌نخورده بماند.
6. هیچ دادهٔ هویتی دانشجو، رمز، کلید، توکن، گزارش محرمانه یا محتوای تاریخی حساس برای ترجمه به اسناد عمومی کپی نشود.

## کنترل کیفیت برای هر PR

- [ ] توضیحات PR و متن‌های جدید/ویرایش‌شدهٔ Markdown فارسی‌اند.
- [ ] لینک‌های فهرست `docs/INDEX.md` و ارجاع‌ها نشکسته‌اند.
- [ ] متن اصلی `LICENSE`، دستورات، کدها و قراردادهای API تغییر نکرده‌اند.
- [ ] گزارش‌های تاریخی برچسب زمانی دارند و وضعیت قدیمی را با امروز اشتباه نمی‌گیرند.
- [ ] مستندات فنی و دفتر تصمیمات با هم سازگارند.
- [ ] تغییرات محصول و امنیت جداگانه تست و روی SHA دقیق بررسی شده‌اند.
- [ ] محتوای فارسی از دادهٔ خصوصی و اعتبارنامهٔ واقعی پاک است.

## پاسخ به متن انگلیسی قدیمی

وقتی سند تاریخی یا گزارش قبلی هنوز انگلیسی است، همان سند را در یک PR بازبینی و فارسی کنید، بدون حذف اطلاعات مهم یا ساختن ادعای موفقیت تازه. **هیچ مشارکت‌کننده‌ای مجاز نیست دوباره یک سند رسمیِ تماماً انگلیسی ایجاد کند.** برای ثبت موارد باقی‌مانده، یک Issue یا فهرست غیرحساس در دفتر تصمیم‌ها به‌روز شود؛ تا زمانی که پوشش اسناد کامل نشده، ادعای «صد درصد فارسی‌شده» مجاز نیست.
