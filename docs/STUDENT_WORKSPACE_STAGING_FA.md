# مسیر میز کار دانشجو و آمادگی انتقال به سرور

> وضعیت: توسعه در محیط دمو. این دستورالعمل مجوز راه‌اندازی واقعی یا تأیید آیین‌نامه دانشگاه آزاد نیست.

## اصلاحات مسیر دانشجو

- شش بخش قابل دسترس در میز کار: دروس، پیشنهادها، برنامه من، کارنامه، پشتیبانی و گزارش باگ؛ ناوبری شبکه‌ای با دکمه‌های مناسب لمس در موبایل.
- در شروع/بازبارگذاری صفحه، **برنامه ذخیره‌شده ابتدا خوانده می‌شود** و همان انتخاب‌ها برای تحلیل تطبیقی فرستاده می‌شوند.
- انتخاب/حذف گروه به API ارسال می‌شود؛ تنها در صورت پاسخ موفق، انتخاب در رابط کاربری ثبت می‌شود. تصمیم قطعی درباره صلاحیت علمی همچنان با Backend است.
- عملیات تغییر برنامه هم‌زمان اجرا نمی‌شوند تا آخرین ذخیره‌سازی ناخواسته با درخواست قبلی بازنویسی نشود. تغییرات هم‌زمانِ اضافی به‌صورت خودکار صف‌بندی نمی‌شوند؛ کاربر باید پس از پایان ذخیره‌سازی دوباره تلاش کند.
- خطای دریافت اطلاعات و خطای ذخیره‌سازی جدا نمایش داده می‌شوند. نمایش «ثبت شد» فقط پس از پاسخ موفق است؛ در شکست API، وضعیت قبلی حفظ می‌شود.
- پاسخ قدیمی ارزیابی نمی‌تواند نتیجه ارزیابی جدیدتر را جایگزین کند.
- قرارداد API در `PUT /api/student/plan` برای اولویت‌ها اکنون فهرست ترتیبی شناسه‌ها یا نقشه رتبه‌ها را می‌پذیرد و برای ذخیره نقشه رتبه تولید می‌کند؛ ساختار ذخیره‌شده `StudentPlan.coursePriorities` تغییر نمی‌کند. داده واقعی دانشجو به دمو منتقل نمی‌شود.
- `POST /api/student/plan/select` در کنار فیلدهای سازگار با مشتری‌های قبلی، `data.selectedOfferingIds` و `data.plan` نیز برمی‌گرداند.

## استقرار آزمایشی آینده، بدون ساخت سرور در این مرحله

1. یک میزبان **Node.js 22 یا جدیدتر** با TLS reverse proxy انتخاب شود؛ تا اتصال امن و مجوزها تأیید نشده‌اند، دسترسی عمومی باز نشود.
2. `DARSCHYN_DATA_DIR` به مسیر دائمی **خارج از checkout گیت‌هاب** اشاره کند؛ مالکیت فایل و پوشه برای حساب سرویس باشد و فایل JSON دارای مجوز محدود مانند `0600` باشد.
3. متغیرهای `JWT_SECRET`، `ROOT_OWNER_MOBILE`، `ROOT_OWNER_PASSWORD` و `ROOT_OWNER_RECOVERY_KEY` در secret manager یا فایل خصوصی سرویس تعریف شوند؛ **هیچ مقدار واقعی در ریپو، PR یا لاگ قرار نگیرد**.
4. قبل از اجرای سرویس، در همان محیط با مقادیر واقعیِ ذخیره‌شده خارج از گیت‌هاب: `node scripts/staging-preflight.cjs`. این دستور **فقط بررسی می‌کند** و دیتابیس نمی‌سازد. سپس `bun run verify` و `bun run smoke:api` را در محیط ایزوله اجرا کنید.
5. روی دیتابیس **کاملاً ساختگی** ورود، کنترل دسترسی، ویرایش و ذخیرهٔ برنامه، قطع API، راه‌اندازی مجدد، backup/restore و APIهای 401/403/404 تست شود. تا تکمیل این معیارها داده دانشجوی واقعی وارد نشود.
6. اگر چند نمونه سرور هم‌زمان، چند کاربر سنگین یا وظایف موازی لازم باشد، نگهداری JSON فعلی برای محیط عملیاتی کافی نیست؛ مهاجرت ذخیره‌سازی باید جداگانه طراحی و آزموده شود.

### هشدار مهم

- `scripts/staging-preflight.cjs` یک کنترل محدود و محلی است، **نه ممیزی امنیتی، آزمون کیفیت رمز، آزمون TLS، بررسی نسخهٔ پشتیبان یا تأیید آمادگی انتشار**.
- فایل دیتابیس قدیمی که در گیت‌هاب track شده طبق [Issue #4](https://github.com/mohammadrezamie/DarsChin/issues/4) باید پیش از هر استقرار عمومی از نظر داده حساس بررسی و ایمن‌سازی شود.
- Preview فعلی Vercel به API دائمی مجهز نیست: [Issue #16](https://github.com/mohammadrezamie/DarsChin/issues/16).
- سهمیه استقرار Vercel در ۲۰۲۶/۱۰/۲۵ محدود شده: [Issue #24](https://github.com/mohammadrezamie/DarsChin/issues/24). تا آزادشدن ظرفیت نباید ادعای لینک Preview تازه کرد.

## اعتبارسنجی لازم قبل از Merge و انتشار

- `bun run verify` روی همان SHA منتخب، به‌ویژه تست‌های `student-plan-reliability` و `staging-preflight`.
- بررسی ۳۲۰، ۳۷۵ و ۴۳۰ پیکسل در Safari و Android Chrome، تب‌های پشتیبانی/باگ، تداخل ساعت، وضعیت ذخیره‌شدن و حالت‌های شکست API.
- آزمون تأییدشده‌ی درخواست نامعتبر به `PUT /api/student/plan` و `POST /api/student/plan/select` که وضعیت ذخیره‌شده را تغییر ندهد.
- عدم تغییر قوانین دانشگاه آزاد بدون مستند رسمی تأییدشده.

این سند نقشهٔ اجرایی است و جای گزارش واقعی اجرای تست یا استقرار را نمی‌گیرد.
