# شیوه همکاری تیم روی GitHub و Vercel

## شاخه‌ها

- `main`: کد پذیرفته‌شده؛ Vercel آن را به Production متصل کرده است. Push مستقیم ممنوع در فرایند تیمی.
- `develop`: نمای نمایشی قابل مشاهده برای بررسی و گزارش باگ؛ فقط پس از تست وارد شود.
- `feat/*`, `fix/*`, `docs/*`: تغییر مستقل هر نفر. PR برای Review باز شود؛ کار ناتمام Draft بماند.

## آیا Commit همکار Vercel را به‌روز می‌کند؟

بله، Vercel با GitHub یکپارچه است: Push به هر شاخهٔ غیر Production معمولاً Preview می‌سازد؛ Merge/Push به `main` نسخه Production را به‌روز می‌کند. **ولی** در ریپوی خصوصی، نویسنده Commit باید در Vercel مجاز و حساب Vercel او به Git متصل باشد؛ وگرنه Deployment می‌تواند Block شود. بنابراین دسترسی Write در GitHub به‌تنهایی تضمین Deploy نیست.

هنگام بررسی ۲۰۲۶/۱۰/۲۵، تیم Vercel متصل فقط **یک عضو با نقش Owner** داشت. اگر همکاران Commit کنند، قبل از اینکه به انتشار اتکا شود باید دسترسی و پلن تیم Vercel بازبینی شود.

## پاک‌سازی شاخه‌های کاری

- فقط `main` و `develop` دائمی هستند.
- پس از ادغام موفق یک PR، شاخهٔ `feat/*`، `fix/*` یا `docs/*` را حذف کنید؛ نخست SHA و وضعیت Merge را تأیید کنید و مطمئن شوید Commit انحصاریِ ادغام‌نشده ندارد.
- شاخه‌های PR **بسته و ادغام‌نشده** را بدون بررسی Diff و دلیل بسته‌شدن حذف نکنید. اگر PR جایگزین شده، شمارهٔ PR جایگزین را ثبت کنید و بعد حذف کنید.
- یک قابلیت جدید = یک شاخهٔ کوتاه‌عمر و یک PR؛ از نگهداری شاخه‌های موازی طولانی خودداری کنید.
- در زمان بررسی ۲۰۲۶/۱۰/۲۵ شاخه‌های قدیمی `fix/ci-regression-tests` (PR #1) و `fix/redact-sensitive-admin-exports-20261024` (PR #5) هنوز باقی بودند؛ PRها بسته و ادغام‌نشده‌اند و نسخه‌های بازطراحی‌شده/امن‌تر در PRهای #9 و #8 منتشر شده‌اند. پاکسازی این دو پس از تأیید نهایی عدم وجود Commitهای منحصربه‌فرد انجام شود.

## الگوی PR

1. شاخه را از `develop` به‌روز بگیر.
2. یک تغییر مشخص را پیاده کن؛ با داده واقعی دانشجویان کار نکن.
3. `bun run verify` و برای API، `bun run smoke:api`؛ خروجی و Commit دقیق در PR.
4. نوع تغییر مشخص باشد: «UI»، «Backend»، «Data»، «Academic Policy».
5. هیچ قانون دانشگاهی بدون ثبت تأیید در `ACADEMIC_RULES_INTAKE_FA.md` تغییر نکند.
6. مرورگر، موبایل، خطاها و لینک Preview را در PR درج کن.
7. بعد از بازبینی Merge به `develop`؛ ارتقا به `main` با PR جدا و تصمیم انتشار.

## گزارش باگ از نسخه زنده

- URL کامل Preview + شماره Commit
- تاریخ، مرورگر و اندازه صفحه
- اطلاعات غیرشخصی درباره حساب یا سناریوی آزمایشی
- مراحل بازتولید: ۱، ۲، ۳
- رفتار مورد انتظار و رفتار واقعی
- متن پیام خطا، Screenshot بدون شماره موبایل/توکن
- فراوانی و شدت مشکل

از Issues در مخزن استفاده کن. **هیچ رمز، کوکی، JWT، فایل دانشگاهی یا مشخصات واقعی افراد را داخل Issue نگذار.**
