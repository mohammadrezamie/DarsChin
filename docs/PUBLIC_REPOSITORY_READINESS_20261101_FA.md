1. فایل JSON دادهٔ عملیاتی از index این شاخه خارج شده است؛ **هیچ فایل یا داده‌ای در VPS، Production یا TNA دست‌کاری نشده است.** پیش از merge بررسی کنید سرویس هیچ‌وقت دیتابیس زنده را از checkout مخزن نمی‌خواند و در upgrade فایل در حال استفاده حذف نمی‌شود.
2. `scripts/check-public-source.cjs` برای جلوگیری از commit تصادفی دیتابیس محلی، ENV خصوصی، کلیدهای خصوصی و فایل‌های اعتبارنامه اضافه شد. فقط **مسیرهای tracked** را بررسی می‌کند؛ فایل‌های کاری/شخصی را نمی‌خواند یا پاک نمی‌کند.

## شروط الزامی برای تغییر Visibility

- [ ] **تعیین وضعیت دادهٔ غیرنمونه:** با مالک داده مشخص شود رکورد غیردمو واقعی است یا نه. تا آن زمان محرمانه تلقی شود.
- [ ] **حفاظت و مهاجرت دیتابیس:** از دیتای فعلی VPS نسخهٔ پشتیبان خارج از Git با دسترسی محدود بگیرید؛ مسیر `DARSCHYN_DATA_DIR` و `DARSCHYN_REQUIRE_EXISTING_DB` را بررسی و در محیط تست boot/restart/restore را با فایل خارج از repo اثبات کنید. حذف فایل Git نباید منجر به حذف دیتای زنده یا seed شدن حساب‌ها شود.
- [ ] **پاک‌سازی تاریخچهٔ کامل:** پس از تأیید صریح مالک برای بازنویسی مخرب تاریخچه، از تمام refs و وضعیت قبل، backup مطمئن بگیرید. با `git filter-repo` یا ابزار معادل، مسیر `data/darschyn-db.json` و هر فایل حساس دیگر را از **تمام Branchها و Tagها** حذف کنید؛ سپس clone تازه و `git log --all` و objectها را بررسی کنید. بازنویسی history نیازمند force-push هماهنگ، به‌روزرسانی cloneها و بازبینی PRهای باز است؛ صرفاً `git rm` کافی نیست.
- [ ] **کاهش پیامد افشا:** شماره تماس/هویت غیردمو، recoveryKey، هش رمز، توکن‌ها و هر رمز عبور احتمالی گذشته را با حداقل دسترسی ارزیابی کنید؛ recoveryKey را باطل/تعویض کنید و در صورت کاربردی بودن اعتبارنامه‌ها، رمز را Reset و نشست‌ها را revoke کنید. اطلاعات شخصی را در گزارش عمومی منتشر نکنید.
- [ ] **اسکن جامع:** اسکن محتوامحور secrets و PII روی همهٔ branch/tag/commit، سورس افزونه و هر دو ZIP، مستندات، فایل‌های استقرار، issueها/PRها، Releases و Actions logs انجام شود. ابزار جلوگیری از commit تنها بخش کوچکی از این گیت است.
- [ ] **گیت تست:** روی SHA دقیق نهایی، `bun install --frozen-lockfile` و `bun run qa:full` و تست بازگشت‌پذیری داده پاس شود. هیچ Preview یا Build قدیمی جای این آزمون را نمی‌گیرد.
- [ ] **قوانین مشارکت:** بعد از تغییر Private → Public، GitHub همهٔ push rulesetها را غیرفعال می‌کند؛ تنظیمات باید بلافاصله پس از تغییر بازبینی/فعال‌سازی شوند. Branch protection/Ruleset برای `main`، PR Review، حداقل دسترسی workflow token، Secret Scanning/Push Protection (در صورت دسترس)، وابستگی‌ها و سیاست گزارش امن ضعف‌ها بررسی شود.
- [ ] **نسخهٔ نهایی و انتشار:** همهٔ refs بررسی شوند، backup معتبر حفظ شود، سپس فقط با تأیید مالک Visibility عوض شود. مجوز انتشار/لایسنس متن‌باز **تصمیم جداگانه** است؛ Public بودن به‌خودی‌خود مجوز کپی و توزیع نمی‌دهد.

## پیشنهاد انتشار کم‌ریسک‌تر: مخزن عمومیِ تمیز

با توجه به وجود اطلاعات حساب غیرنمونه در گذشتهٔ این مخزن و وجود PRهای قدیمی، **امن‌ترین مسیر قابل پیشنهاد این است که مخزن اصلی Private بماند** و یک مخزن عمومی **جدید، با تاریخچهٔ مستقل و صرفاً سورس پاک‌سازی‌شده** منتشر شود.

1. ابتدا شاخهٔ آماده‌سازی را بازبینی و QA کنید و خروجی سورس پاک‌شده را از یک checkout مستقل تهیه کنید؛ هرگز پوشهٔ `.git`، دیتابیس، ENV و backupهای شخصی را منتقل نکنید.
2. اسکن کد، فایل‌های ZIP افزونه، مجوزهای انتشار و وابستگی‌ها را روی همان خروجی کامل کنید.
3. در مخزن عمومی جدید فقط یک commit آغازینِ پاک‌سازی‌شده بسازید و CI حداقلی را روی همان SHA اجرا کنید. یک مخزن عمومیِ تازه به‌خودی‌خود از تاریخچهٔ commits/PRهای مخزن خصوصی نسخه‌برداری نمی‌کند.
4. اتصال deploymentها، Vercel، issueها و سایر لینک‌ها فقط با تصمیم مستقل مالک و بعد از بازبینی انجام شود.

**گزینهٔ تغییر Visibility همین مخزن** پیچیده‌تر است: `git filter-repo` و force-push لزوماً همهٔ refs مخفی Pull Request، cached diffها، forkها و نسخه‌های قدیمی GitHub را پاک نمی‌کنند. ممکن است برای حذف محتوای حساس از cached views و refs سرور نیاز به هماهنگی با پشتیبانی GitHub باشد. تا تأیید حذف تمام راه‌های دسترسی، این مخزن را Public نکنید.

## ملاحظات GitHub Actions

- استفادهٔ رایگانِ نامحدود دقیقه فقط برای **Runner استاندارد** و مخزن عمومی است؛ محدودیت هر Job، فضای Artifact و larger runners جدا هستند.
- برای مصرف بهینه: batch کردن تغییرات، cancellation در concurrency، اجرای تست یک‌بار برای هر SHA و جلوگیری از Triggerهای تکراری اهمیت دارد. `main-quality-gate.yml` اکنون فقط روی push به main و اجرای دستی است، پس تا قبل از اصلاح سیاستِ PR نباید نتیجهٔ PR را سبز فرض کرد.
- *صرفاً برای عمومی‌شدن مخزن* لازم نیست همهٔ backlogهای UI/UX یا موتور درسی تکمیل شوند، ولی انتشار دادهٔ خصوصی، credential فعال، تاریخچهٔ افشاگر یا خطاهای امنیتی حل‌نشده قابل قبول نیستند.
