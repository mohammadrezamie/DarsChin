# نقشه اجرای پایلوت درس‌چین و راه‌اندازی VPS

**دامنهٔ فاز اول:** کارشناسی مهندسی برق، دانشگاه آزاد اسلامی واحد علوم و تحقیقات. نسخه‌های بعدی می‌توانند واحدها، مقاطع، رشته‌ها و سال‌ورودی‌های بیشتری داشته باشند؛ ساختار دیتابیس از ابتدا شناسهٔ واحد، مقطع، رشته، سال ورود و نیمسال را جدا نگه می‌دارد.

> وضعیت: دمو و آزمون داخلی. چارت مصوب، شناسهٔ اساتید، ظرفیت واقعی، آیین‌نامه و منبع ارائه‌های ترمی هنوز باید با مدارک رسمی کنترل شوند. نمایش «دموی برق علوم و تحقیقات» به معنی تأیید دانشگاه یا دانش‌بنیان بودن سامانه نیست.

## ۱. ورود آزمایشی و تست زنده بدون سرور

| نشانی | کارکرد |
| --- | --- |
| `/demo/student` | پنل کاملِ آزمایشی دانشجو؛ برنامه هفتگی، دروس، کارنامه، پیشنهادها، تیکت، خطا، ورود فایل |
| `/demo/admin` | پنل کاملِ آزمایشی مدیر؛ جست‌وجوی بخش‌ها، CRUD داده‌های نمونه، بررسی تطبیق و مدیریت |
| `/demo` | برنامه‌ریز ساده برای تست تداخل کلاس‌ها و نمایش زمان پیوسته |
| `/login` | ورود واقعی با سرور؛ لینک‌های مستقیم ورود دمو هم در همین صفحه هستند |

دمو **بدون JWT، رمز عبور، پیامک و درخواست API واقعی** اجرا می‌شود. داده‌های آن ساختگی و فقط در `localStorage` همان مرورگر ذخیره می‌شوند؛ با «بازنشانی دمو» حذف می‌شوند. حساب مدیریتِ دمو هیچ نقش واقعی روی سرور ندارد. هر مسیری که شبیه‌سازی نشده باید خطای صریح بدهد، نه موفقیت ساختگی. قابلیت‌هایی مثل قوانین نهایی دانشگاه، اتصال واقعی آموزشیار و گزارش سلامت سرور **با دمو قابل تأیید نیستند**.

رابط با `dir=rtl` طراحی شده است: همبرگر و کشو سمت راست، تغییر تم روز/خودکار/شب در هدر. برنامه هفتگی به‌صورت زمان پیوسته از ۰۷:۰۰ تا ۲۰:۰۰، تمام دقیقه‌ها و هفت روز را پوشش می‌دهد. کلاس بدون زمان معتبر یا خارج از این محدوده با هشدار پایین جدول باقی می‌ماند.

### ثبت خروجی تست پایلوت

دکمهٔ «گزارش باگ دمو» در پنل دانشجو، مدیر و برنامه‌ریز ساده امکان ثبت مراحل تکرار خطا، انتظار، نتیجهٔ واقعی و اهمیت را می‌دهد. این گزارش را می‌توان **کپی** کرد یا با «دریافت گزارش متنی» در یک فایل UTF-8 ذخیره کرد و بعداً در Issue گیت‌هاب استفاده کرد. این فرم هیچ گزارشی را به سرور نمی‌فرستد؛ اطلاعات هویتی دانشجو یا توکن را در متن ننویسید.

**تفاوت ثبت در GitHub و استقرار زنده (۲۵ اکتبر ۲۰۲۶):** تمام قابلیت‌های تازه روی `main` ثبت شده‌اند، ولی Vercel درخواست استقرار جدید را با HTTP 402 و محدودیت `api-deployments-free-per-day` رد کرده است. آخرین استقرار READY مشاهده‌شده نسخهٔ قدیمی‌تری از `main` است و صحت لینک‌های مستقیم و تمام قابلیت‌های تازه روی آن تأیید نشده. GitHub Actions هم بدون اختصاص Runner در چند ثانیه ناموفق شده است؛ وجود تست در ریپو را با اجرای موفق اشتباه نگیرید.

## ۲. راه‌اندازی VPS تک‌سروری در اولین فرصت

**پیش‌نیاز:** یک VPS لینوکس با Docker Engine + Compose plugin، دامنه‌ای که DNS آن به VPS اشاره کند، دسترسی پورت‌های 80/443 برای صدور TLS، رمز اختصاصی قوی برای مدیر ریشه و بک‌آپ جداگانه. شبکه و فایروال را قبل از راه‌اندازی محدود کنید.

```bash
git clone https://github.com/mohammadrezamie/DarsChin.git
cd DarsChin
cp deploy/.env.vps.example deploy/.env.vps
chmod 600 deploy/.env.vps
# Edit deploy/.env.vps locally: domain, email, JWT, root mobile/password/recovery key.
# Generate JWT_SECRET and recovery key separately with: openssl rand -hex 32
docker compose --env-file deploy/.env.vps config -q
docker compose --env-file deploy/.env.vps up -d --build
docker compose --env-file deploy/.env.vps ps
curl -fsS https://YOUR_DOMAIN/api/health
```

- `Dockerfile` خروجی فرانت و بک‌اند را از `bun.lock` می‌سازد و در Node.js اجرا می‌کند.
- `compose.yaml` یک نمونه Node (برای JSON DB) و یک Caddy HTTPS دارد؛ پورت Node مستقیماً روی اینترنت منتشر نشده است.
- `DARSCHYN_DATA_DIR=/app/data` روی volume نام‌دار `darschin-data` ذخیره می‌شود؛ با به‌روزرسانی کانتینر پاک نمی‌شود.
- کلید JWT و اطلاعات ورود ریشه را **در فایل واقعی خصوصی** نگه دارید؛ فایل `.env.vps` نباید در Git یا خروجی پشتیبانی قرار گیرد.
- در اولین اجرای production، کاربران ساختگی دارای رمز ثابت ایجاد نمی‌شوند. برای پایلوت سرویس، تنها حساب ریشه با مقادیر خصوصی ایجاد می‌شود. محیط `/demo/*` همچنان بدون حساب واقعی در فرانت است.
- هنگام راه‌اندازی با دیتابیس قدیمی، دو کاربر seed شناخته‌شده حذف می‌شوند؛ مهاجرت‌ها و تصمیم‌های بررسی موجود حفظ می‌شوند. اگر دیتابیس تولیدی خراب باشد سرویس به‌جای بازنویسی با seed **متوقف می‌شود**.
- بعد از ویرایش کد: روی commit مشخص `bun run verify` و `bun run smoke:api` را در محیط تست ایزوله اجرا کنید، سپس سرویس را به‌روزرسانی کنید. **فایل‌های این تنظیمات در Git ثبت شده‌اند ولی هنوز استقرار واقعی روی VPS آزمایش نشده است.**
- Caddy گواهی خودکار TLS را می‌گیرد؛ اگر هنوز دامنه یا DNS آماده نیست، ورود واقعی کاربران را به اینترنت باز نکنید و ابتدا در محیط داخلی تست کنید.

## ۳. پذیرش فاز اول

1. روی گوشی واقعی و دسکتاپ، صفحه اصلی و سه مسیر دمو باز شوند؛ همبرگر راست، جست‌وجوی پنل، و سه حالت تم تست شوند.
2. دانشجوی فرضی بتواند درس نمونه انتخاب کند، تداخل ساعت را ببیند و برنامه خود را در مرورگر حفظ کند.
3. مدیر نمونه بتواند بخش‌های پنل را جست‌وجو کند، دادهٔ نمایشی را تغییر دهد و گردش تأیید/رد تطبیق فایل را بدون انتشار سراسری آزمایش کند.
4. تقویم ۷ تا ۲۰ و کلاس‌های نامشخص، زودتر و دیرتر از محدوده بررسی شوند.
5. تست Browser و TypeScript و Build برای SHA منتشرشده و پس از آن Smoke با API مستقل روی VPS اجرا شوند.
6. تا دریافت سند چارت و مقررات پایلوت، خروجی Eligibility و پیشنهادها در دمو فقط «ساختگی» محسوب شوند.

## ۴. توسعه تدریجی به دانشگاه کامل

فاز A: دمو و تست UX/باگ‌یابی برای برق کارشناسی علوم تحقیقات.  
فاز B: تأیید مستندات چارت و مقررات همان پایلوت، شناسایی منبع معتبر ارائه‌های ترمی، تأیید نقش‌های واقعی.  
فاز C: پایگاه دادهٔ تراکنشی (به‌جای JSON تک‌فرآیندی)، نسخه‌بندی قواعد، مهاجرت و بازیابی تست‌شده، گزارش ممیزی و کنترل دسترسی واحد/رشته.  
فاز D: توسعهٔ مرحله‌ای رشته/واحد/مقطع با قراردادهای داده و تستِ جداگانه؛ هیچ قانون یک واحد به‌صورت پیش‌فرض بر کل دانشگاه تعمیم داده نشود.

**هشدار عملیاتی:** JSON DB برای چند پردازش، چند VPS یا همگام‌سازی همزمان مقاوم نیست؛ روی یک نمونه Node باقی بمانید تا به PostgreSQL/دیتابیس تراکنشی مهاجرت شود. نسخهٔ مرورگری Vercel API ماندگار ندارد و جایگزین VPS نیست.
